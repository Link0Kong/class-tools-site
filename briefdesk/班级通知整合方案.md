# Briefdesk 班级通知整合方案

> **微信人工转发私聊 + QQ 群自动采集 → 班级工具站 + QQ 频道** ｜ v1.1 ｜ 2026-11-03
>
> 目标：把班级分散在 QQ 群、微信群、私聊里的通知，汇成一份**自动分类、去重、带截止时间、可检索**的班级简报；完善后**整合进班级工具站（tool.furina.fun）**，重要简报可**同步发布到 QQ 频道相关板块**，并尽量兼容通知里常见的**公众号文章、小程序卡片、腾讯文档收集表**等富媒体内容。
> 适用对象：福建中医药大学 2026 级信管 · 班委（副团支书）管理员 · 单机本地部署。
> 本次同时交付**示例网页**：`web/tools/notice-demo.html`（见 §5.10），先把「最终长什么样」定下来。

## 0. 结论先行（TL;DR）

1. **用 Briefdesk（简报台）做中枢。** 它已经内置了「多消息源采集 → 图片 OCR → AI 分类 → 语义去重 → 同话题合并 → SQLite → 网页卡片/日历/提醒/问答」整条链路，属于**配置即用**，不需要重写应用。
2. **QQ 侧全自动（主力）。** 本机 QQ NT 登录班级群 → `qqflow-server` 只读解密本地 `nt_msg.db` → Briefdesk 的 `qqflow` 插件采集。**不需要群机器人、不需要群主授权、不需要企业资质**，群消息全量可读（含非 @ 消息与历史）。
3. **微信侧以「人工转发」为主。** 私聊通知由你（或班委）手动转发进一个**收件箱会话**，再由采集链路自动读走：
   - 方案 A（进阶）：`weflow-server` 只读本机微信 4.x 本地库，收件箱用微信「文件传输助手」，**一键转发后全自动**；
   - 方案 B（零风险，默认起步）：微信内容人工复制/截图到 **QQ「班级简报收件箱」群**，由 QQ 链路自动采集。
   - **唯一硬门槛**：方案 A 需要一次性提取微信数据库密钥（外部工具，微信 4.1+ 需 passphrase 派生）。**拿不到就退回方案 B，QQ 侧完全不受影响。**
4. **AI 默认跑本机 Ollama**（qwen3:14b + nomic-embed-text）：零成本、消息不出本机、实测 JSON 分类可用。云端模型只作为可选加速通道（换成任意 OpenAI 兼容端点即可），不绑定具体厂商。
5. **最终形态：整合进班级工具站 + QQ 频道同步发布。** Briefdesk 在本地完成采集与加工 → 人工确认 → 精选通知写入 CloudBase `notices` 表 → **tool.furina.fun 通知板块**自动展示；每日简报/重要通知可同步到 **QQ 频道的公告栏 / 学习互助 / 活动报名**（§5.7、§5.8）。
6. **富媒体通知尽量可用**：公众号文章、腾讯文档收集表可直接展示与打开；小程序卡片、群文件、图片 OCR、通用链接都有**展示 + 降级**方案，不追求 100% 还原微信卡片，保证「信息可读、入口可点、关键内容不丢」（§5.9）。
7. **成本与周期**：软件 0 元；P0 半天内看到第一张真实卡片；完整落地约 2–3 天（不含观察期）；常开电费约 20–30 元/月。
8. **最大不确定性**：微信 4.1.15.13 与密钥提取工具的兼容性。给它半天时间盒，失败立即走 Plan B。

## 1. 需求与设计边界

### 1.1 要做的事

| # | 需求 | Briefdesk 对应能力 |
|---|------|-------------------|
| 1 | **汇总**：QQ 班级群 / 学院通知群 / 课程群；微信群（可选）；私聊通知（人工转发） | 多消息源插件（qqflow / weflow）+ 群聊筛选 |
| 2 | **分类**：教务、团务、作业、考试、活动、缴费、班级事务…… | AI 分类（类别/提示词/颜色可自定义） |
| 3 | **去重合并**：同一条通知在多个群转发，只留一张卡并标注多来源 | 语义去重 + 同话题合并 |
| 4 | **时间**：自动识别截止时间，进日历、到期提醒 | 中文时间解析（temporal）+ 日历 + 提醒 |
| 5 | **检索**：问「这周有什么作业」「哪天交表」 | RAG 问答（基于嵌入向量） |
| 6 | **推送（可选）**：每天一份简报 → 手机 | 需新增 Web 插件（方案见 §5.6） |
| 7 | **对外展示**：完善后整合进班级工具站（tool.furina.fun）通知板块 | CloudBase `notices` 表 + 静态站现有通知渲染（§5.7） |
| 8 | **频道同步**：重要简报/通知同步到 QQ 频道相关板块 | 频道机器人 API（§5.8） |
| 9 | **富媒体**：公众号文章、小程序卡片、腾讯文档收集表、群文件、截图 | 已有部分 + 新增解析/降级（§5.9，示例页已演示） |

### 1.2 不做的（红线）

- ❌ 不自动回复、不自动群发、不代替你在群里发言。
- ❌ 不监控无关私聊；不采集与班级无关的群。
- ❌ 不把聊天数据放公网 / 云端（AI 默认本地）。
- ❌ 不用协议机器人（NapCat/LLOneBot 等）登录微信 / QQ——封号风险高，且违反平台协议。
- ❌ **工具站/QQ 频道只发「确认过的精选通知或简报」**，不把原始聊天记录整段推上去；含同学个人信息的内容不上公网。

### 1.3 决定方案形状的现实约束

- **微信没有官方群消息 API**；hook / 协议端风险高 → 只能「本地库只读」或「人工转发」。
- **QQ 官方机器人**虽然 2026-10 起支持「接收所有消息」全量模式，但需要**企业资质 + 群主在机器人后台开启 + 逐群添加机器人**，学生身份不现实；本地库只读是唯一低成本全量路径。
- **Briefdesk 只监听 `127.0.0.1`**，且有 Host/Origin 白名单（`server/middleware.py`）→ 手机直接访问局域网 IP 会 400，需要反代（§5.6）。
- **采集依赖本机登录态**：微信 / QQ 必须在本机保持登录；本机关机或客户端掉线期间的消息，只能靠客户端重新登录后同步到的部分补齐——所以建议常开 + 看门狗。

## 3. 总体架构

三层：**采集层 → 服务层 → 处理层 → 应用层**。

| 层 | 组件 | 职责 |
|----|------|------|
| 采集 | 微信（本机登录）+ weflow-server（可选） | 读微信群 / 文件传输助手（只读） |
| 采集 | QQ NT（本机登录）+ qqflow-server | 读班级 QQ 群（只读） |
| 采集 | 人工转发 | 私聊通知 → 收件箱会话 |
| 服务 | Briefdesk 消息源插件 | 轮询 + SSE 接入，会话级水位 |
| 处理 | OCR → AI 分类 → 语义去重 → 同话题合并 | 全部可插拔，失败保留待回填 |
| 应用 | Web UI / 日历 / 提醒 / RAG / 每日简报（新增） | 阅读、处理、检索、推送 |

**数据流**：`本机聊天库（加密）→ 只读解密服务 → HTTP/SSE → Briefdesk 管道 → SQLite → 浏览器`。
除「切云端 AI 时的脱敏正文」与「推送出去的简报文本」外，数据不出本机。

## 4. 采集方案

### 4.1 QQ 群（自动采集，主力）

**推荐路径：qqflow-server（本地库只读）。**

**原理**：QQ NT 把消息写进本机 `Documents\Tencent Files\<QQ号>\nt_qq\nt_db\nt_msg.db`（SQLCipher 加密）。`qqflow-server` 用你提供的 16 字节库密钥**只读解密**、建内存索引，通过 HTTP/SSE 输出。它不修改 QQ、不发消息、只监听 `127.0.0.1:5032`。

**前置条件**：
- QQ NT 在本机登录（账号已在班级群内）；**群消息全量可读（含非 @、他人发言），但只管「本地库里已有的」——QQ 不会把入群前的历史补给你**；
- 一次性提取 QQ 本地库密钥（16 字节可打印 ASCII）。官方脚本：QQBackup 的 `qq-win-db-key`（`scripts/windows/ntqq/windows_ntqq_get_key.ps1`），社区确认可用版本 QQ **9.9.32-51246**，本机 9.9.31.49919 大概率可用但**需实测**；不要 `irm | iex` 直接跑远程脚本，先下载读一遍。
- token 在 Windows 凭据管理器（service `qqflow-server` / user `http-api-token`），用 `qqflow-server token` 取（Briefdesk 插件注释里说的 `token.txt` 已过时）。
- 若 QQ 数据不在默认 `Documents\Tencent Files`（如 OneDrive 重定向），注册时**必须显式传 `db_path`**；`db_path` 留空时服务端只能扫默认路径，且要求**先登录 QQ 再启动服务**，否则注册报 `unknown_qq`。

**实施步骤（PowerShell）**：

```powershell
# 1) 下载并校验 qqflow-server v0.10.0（GitHub Releases）
New-Item -ItemType Directory -Force C:\briefdesk\bin\qqflow-server | Out-Null
Set-Location C:\briefdesk\bin\qqflow-server
$ver='0.10.0'; $zip="qqflow-server-$ver-x86_64-pc-windows-msvc.zip"
$base="https://github.com/ren-yc/qqflow-server/releases/download/v$ver"
Invoke-WebRequest "$base/$zip" -OutFile $zip
Invoke-WebRequest "$base/SHA256SUMS" -OutFile SHA256SUMS
$want=((Select-String SHA256SUMS -Pattern ([regex]::Escape($zip))).Line -split '\s+')[0]
$got=(Get-FileHash -Algorithm SHA256 $zip).Hash.ToLower()
if ($got -ne $want) { throw "sha256 mismatch" }
Expand-Archive $zip -DestinationPath .

# 2) 提取 QQ 库密钥（用 QQBackup/QQDecrypt 的 NTQQ Windows 脚本，16 字节 ASCII）
#    把结果保存到 C:\briefdesk\secrets\qqflow.json（收紧 NTFS 权限，不进仓库/网盘）

# 3) 启动服务（长期运行由看门狗托管）
.\qqflow-server.exe --port 5032 --log info 2> C:\briefdesk\logs\qqflow.log
# 另开窗口取 token
.\qqflow-server.exe token

# 4) 注册账号（token 用变量，不要写进命令行历史）
$tok = (.\qqflow-server.exe token).Trim()
$body = @{ qq='<你的QQ号>'; key='<16字节ASCII库密钥>'; db_path='%USERPROFILE%\Documents\Tencent Files\<QQ号>\nt_qq\nt_db\nt_msg.db' } | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5032/api/v1/accounts `
  -Headers @{ Authorization = "Bearer $tok" } -ContentType 'application/json' -Body $body

# 5) 轮询到 ready，验证会话与消息
do { Start-Sleep 2; $a = Invoke-RestMethod -Uri http://127.0.0.1:5032/api/v1/accounts -Headers @{ Authorization = "Bearer $tok" }; $row = $a.accounts | Where-Object { $_.qq -eq '<你的QQ号>' } } until ($row.state -in 'ready','error')
Invoke-RestMethod -Uri "http://127.0.0.1:5032/api/v1/sessions?limit=20" -Headers @{ Authorization = "Bearer $tok" }
```

**能力边界**：
- ✅ 群消息**全量**可读（含非 @、含历史，取决于本机库里存了多久）；一个进程服务一个 QQ 号。
- ⚠️ QQ 退出登录 / 换号后需重新注册；QQ 大版本升级可能改变库结构（锁定版本 + 关注 release）。
- ⚠️ **PC 关机 / QQ 未登录期间**：消息只靠 QQ 客户端登录后同步到本地的部分补齐 → 建议常开 + 保持登录。

**QQ 采集四条路对比**：

| 方案 | 全量群消息 | 历史回填 | 群主配合 | 封号风险 | 结论 |
|------|:---:|:---:|:---:|:---:|------|
| **qqflow-server 本地库只读** | ✅ 本地库内全量（含非 @、他人） | ✅ 本地库已有（无服务器回填） | 不需要 | 低（只读）；key 提取工具是唯一灰区 | **推荐** |
| QQ 官方机器人「全量模式」 | ✅ 开启后每条（`GROUP_MESSAGE_CREATE`） | ❌ 无历史 API，只能在线实时收 | **需要**：群主加 bot + 群设置开「获取群内全部消息」+ 平台审核/上线（沙箱群 ≤20 人且须自己当群主） | 低（官方） | 备选（门槛高、无历史） |
| 协议端 NapCat / LLOneBot / Lagrange | ✅ | ✅ 可拉服务器历史 | 不需要 | **高**（非官方协议/注入） | 不推荐 |
| QQ 群机器人 webhook | ❌ 只能发 | — | — | 无 | 仅可作推送通道 |

> **为什么不用现成的 OpenClaw QQ 机器人？** 你本机已有 `qqbot`（appId 1903774459）。核实结论：它的连接被 OpenClaw Gateway 占用，且定位是 Agent 对话通道（非 @ 消息只进 `historyLimit` 上下文缓冲，不落采集库、无历史回填）。**不能当采集器**；若走官方 bot 路线，得另建一个应用 + 群主配合，且拿不到历史。所以 QQ 采集用 qqflow-server。

### 4.2 微信（人工转发为主，自动为进阶）

先明确目标：微信侧**不是**全量监控私聊，而是「把需要进简报的内容送进来」——这既是隐私边界，也是规避风险的设计。

#### 方案 A（进阶：一键转发后全自动）—— weflow-server 读本机微信库

- **原理**：`weflow-server` 只读解密 `Documents\xwechat_files\<wxid>\db_storage`（微信 4.x，SQLCipher），HTTP/SSE 输出，与 QQ 链路同构。
- **收件箱**：微信「**文件传输助手**」。收到私聊通知 → 长按 → 转发 → 文件传输助手（一键），weflow 自动读出，Briefdesk 只勾选这一个「私聊」会话 + 相关微信群。
- **验证点（P0 必验）**：文件传输助手要能在「设置 → 群聊筛选」的会话列表里以「私聊」类型出现并被勾选；若 weflow 的 `sessionType` 映射异常，退化为「建一个 3 人群当收件箱」（自己 + 小号/班委）。
- **关键坑（必看）**：`IGNORE_SELF=true`（默认）会过滤掉**你自己发的**消息——而文件传输助手里全是你自己发的转发。**必须设 `IGNORE_SELF=false`**，否则一条都进不来。
- **硬门槛**：微信 4.x 每库独立 64-hex 密钥，需外部工具从微信进程内存提取；**4.1+ 明文 raw key 不再常驻内存**，需先取 passphrase 再做 PBKDF2 派生（工具需支持对应版本）。候选工具（**均需自行验证，不作推荐背书**）：`wechat-decrypt`（内存扫描）、`wcdb-key-tool`（passphrase 派生）、`chatlog_alpha`（社区验证到 4.1.5.30）。图片还需单独提取 `img_aes_key` / `img_xor_key`，否则「文本正常、图片坏」。
- **备选路线**：WeFlow 桌面版（对应 Briefdesk 的 `weflow-legacy` 插件，HTTP API :5031）。但它当前**同样要求自备第三方原生解密组件**，绕不开 key，还多一个常开 GUI 应用——不作为首选。
- **风险**：工具读内存，可能被杀软拦截；可能触发微信风控（概率低但非零）；微信升级 / 重登可能轮换 key，需重新提取。
- **成功后的收益**：微信群自动采集 + 私聊一键转发全自动，体验最好。

#### 方案 B（零风险，纯人工转发）—— 微信 → QQ 收件群 → qqflow 自动采集

- 建一个 QQ 群「**班级简报收件箱**」（自己 + 小号 / 可靠舍友，凑够 QQ 建群人数下限即可）；
- 把微信通知**复制文字 / 发截图**到该群；qqflow 自动读，Briefdesk 勾选该群；
- 完全不碰微信数据库、不需要微信 key；代价是每条通知多 2–3 步（复制 → 切 QQ → 粘贴/发图）。
- 与方案 A 的收件箱规范完全兼容：将来拿到 key，可无缝切到「文件传输助手」。

#### 方案 C（备选观察）—— OpenClaw 微信通道桥接

你已有 OpenClaw 的微信通道（`openclaw-weixin`）。若机器人账号能接收好友私聊转发，可加一个小桥接把手动转发喂给 Briefdesk。**但通道对群聊/转发的支持未核实、维护成本不低**，仅在 A/B 都不满意时评估。

#### 微信三方案对比

| 方案 | 自动化程度 | 依赖 | 风险 | 维护 | 建议 |
|------|-----------|------|------|------|------|
| A weflow-server | 群自动 + 私聊一键转发 | 微信 key 提取 | 中 | 微信升级需重取 key | 进阶首选 |
| B 微信→QQ 收件群 | 全人工转发，之后自动 | QQ 链路 | 极低 | 低 | **默认起步** |
| C OpenClaw 桥 | 半自动 | 通道能力未核实 | 低 | 中 | 观察 |

> **决策规则**：P0 阶段给方案 A 的 key 提取 **≤30 分钟**；成功 → 用 A；失败或不放心 → 用 B。QQ 侧不受影响。

### 4.3 收件箱与转发规范（人机协议）

> 这是「人工转发」能不能好用的关键，比代码重要。

- **收件箱位置**：方案 A = 微信「文件传输助手」；方案 B = QQ「班级简报收件箱」群。
- **只做单条转发**。微信的「合并转发（聊天记录）」生成的是特殊卡片，不保证被解析；多条请逐条转发，或截图走 OCR。
- **文字优先**：能复制文字就别截图；截图会被 OCR，但可能错字/漏行。
- **每条加一行来源**：`【来源：辅导员私聊 11-03】`、`【来源：计算机导论课程群】`。因为 Briefdesk 卡片只显示会话名（收件箱里全是"文件传输助手"），来源前缀能救命。
- **隐私先过一遍**：手机号 / 学号 / 宿舍号不需要进简报的删掉；Briefdesk 会自动脱敏手机号/身份证/邮箱，但姓名、群名不脱敏。
- **语音 / 视频不处理**：重要语音先转文字或截图。
- **群公告告知**：在班级群 / 收件群说明「消息会被汇总到我的本地简报，仅自己使用、不外传」。

### 4.4 采集范围清单（建议）

| 来源 | 是否接入 | 备注 |
|------|:---:|------|
| QQ 班级群 | ✅ | 主战场 |
| QQ 学院 / 年级通知群 | ✅ | 通知密集 |
| QQ 课程群 | ✅ | 作业/考试信息 |
| QQ 社团 / 活动群 | 按需 | 太多会稀释简报，建议先不接 |
| 微信班级群 / 学院群 | 方案 A 时 ✅ | 方案 B 不接（避免重复采集） |
| 微信「文件传输助手」 | 方案 A 时 ✅ | 私聊通知收件箱（`IGNORE_SELF=false`） |
| QQ「班级简报收件箱」 | 方案 B 时 ✅ | 私聊通知收件箱（`IGNORE_SELF=false`） |
| 其他私聊 / 公众号 / 私人小群 | ❌ | 红线：不监控 |

## 5. Briefdesk 配置与改造

### 5.1 安装（推荐源码 / editable 模式）

> 为什么不用 `pip install briefdesk`：wheel 模式**不读**项目 `.env`（`briefdesk/paths.py:99-129`），配置只能走环境变量或设置页，运维麻烦；源码 / editable 模式才读项目根 `.env`。

```powershell
# 目录规划
# C:\briefdesk\
# ├─ app\        git clone briefdesk（源码）
# ├─ venv\       Python 虚拟环境
# ├─ bin\        weflow-server / qqflow-server
# ├─ secrets\    密钥配置（收紧 ACL，不进 Git / 网盘）
# ├─ logs\
# └─ scripts\    start-all / watchdog / backup

git clone https://github.com/ren-yc/briefdesk C:\briefdesk\app
python -m venv C:\briefdesk\venv
C:\briefdesk\venv\Scripts\python -m pip install -U pip
C:\briefdesk\venv\Scripts\pip install -e "C:\briefdesk\app[ocr]"   # OCR 建议装（截图通知多）
Copy-Item C:\briefdesk\app\.env.example C:\briefdesk\app\.env
```

首次启动（前台验证）：`cd C:\briefdesk\app; C:\briefdesk\venv\Scripts\python -m briefdesk` → 浏览器 `http://localhost:3000`。

### 5.2 关键配置（`.env` 摘要）

| 变量 | 建议值 | 作用 / 为什么 |
|------|--------|--------------|
| `PLUGINS` | `["qqflow"]` 起步；A 成功后 `["qqflow","weflow","ocr"]` | 显式启用可选插件 |
| **`IGNORE_SELF`** | **`false`** | **关键**：收件箱里的转发是你自己发的，默认 `true` 会全部过滤 |
| `BACKFILL_HOURS` | 首次 `168`，稳定后 `24` | 首次拉 7 天历史；`-1` = 全量（慎用，AI 调用量激增） |
| `POLL_INTERVAL_SECONDS` | `600` | SSE 断线兜底，每 10 分钟补一次 |
| `MERGE_WINDOW_MINUTES` | `10`（默认） | 同会话同话题片段合并窗口 |
| `AI_API_BASE` | `http://127.0.0.1:11434/v1` | 本地 Ollama（OpenAI 兼容） |
| `AI_MODEL` | `qwen3:14b` | 本机已有模型 |
| `AI_API_KEY` | `ollama`（任意非空） | Ollama 不校验 |
| **`AI_REASONING_EFFORT`** | **`off`** | qwen3 思考会吃掉输出 token；off 后 1–3 秒返回 JSON |
| `AI_MAX_CONCURRENCY` | `1` | 本地模型建议 1，避免排队 |
| `AI_JSON_MODE` | `auto` | Ollama 端点自动走 json_object |
| `EMBED_API_BASE` | `http://127.0.0.1:11434/v1` | 嵌入（去重 + RAG） |
| `EMBED_MODEL` | `nomic-embed-text` | 本机已有，768 维 |
| `SERVER_PORT` | `3000` | 网页端口 |
| `DB_PATH` | 不填（默认 `%LOCALAPPDATA%\briefdesk\data\briefdesk.sqlite`） | 通用覆盖入口；默认位置便于备份 |
| `LOG_LEVEL` | `INFO` | 排错时临时 `DEBUG` |

**密钥不写 `.env`**，走系统钥匙串（Windows 凭据管理器）：

C:\briefdesk\venv\Scripts\briefdesk secrets set WEFLOW_WXID
C:\briefdesk\venv\Scripts\briefdesk secrets set WEFLOW_DB_KEYS        # 整份 JSON，自动分片
C:\briefdesk\venv\Scripts\briefdesk secrets set QQFLOW_API_TOKEN
C:\briefdesk\venv\Scripts\briefdesk secrets set QQFLOW_QQ

也可在网页「设置 → 启动配置 → 密钥区」录入，效果相同（不回显明文）。

### 5.3 AI 通道（默认本地，可换任意 OpenAI 兼容端点）

| 通道 | 配置 | 优点 | 代价 |
|------|------|------|------|
| **本地 Ollama**（默认） | `AI_API_BASE=http://127.0.0.1:11434/v1`，`AI_MODEL=qwen3:14b`，`AI_REASONING_EFFORT=off` | 0 元、隐私最好、无配额 | 分类慢一些（热态 1–3s/次）、质量中等 |

### 5.4 分类方案（把默认口径改成班级口径）

Briefdesk 内置 13 类，**默认只启用 5 类**（活动通知 / 社团招新 / 学术 / 交易 / 实习），偏「校园综合信息」。班级通知场景建议在「设置 → 信息分类」里改成：

| 类别 | 收录 | 排除 |
|------|------|------|
| **教务通知** | 选课、调课、考试安排、成绩、学籍、教学检查 | 社团活动 |
| **团务党建** | 团日活动、青年大学习、团员发展、材料上报、评优 | 普通班会通知 |
| **作业与实验** | 课后作业、实验报告、小组任务、提交方式与要求 | 考试安排 |
| **考试与竞赛** | 期中期末、补考、竞赛报名、考场安排 | 日常作业 |
| **班级事务** | 班会、班委、值日、班费、评奖评优、体检 | 学院级通知 |
| **活动与讲座** | 讲座、志愿服务、文体活动、报名 | 收费培训 |
| **缴费与补贴** | 学费/班费/考试费、助学、报销、补贴 | 商品交易 |
| **失物招领** | 捡到/丢失物品、认领方式 | — |
| **其他** | 兜底（建议低优先级、不置顶） | — |

提示词写法参考 Briefdesk 内置类别：每类写两段「收录：…；排除：…；判别：…」，越具体越准。**先启用 5–6 类跑 3 天，再按误判调整**，不要一次上 10 类。

「设置 → 群聊筛选 → 发现新群聊」后勾选：

- QQ：班级群、学院/年级通知群、课程群；

### 5.6 可选增强（按优先级，不阻塞主线）

#### P1 每日简报 + 推送（最有价值的新增）

- **目的**：每天 21:30 生成「今日必看 / 我要做的事（含截止时间）/ 明日提醒」→ 推到你手机。
- **实现**：新增 Web 插件 `digest`（约 300–500 行）：
  1. 定时任务（asyncio）查最近 24h 的 items；
  2. `ctx.ai.chat(...)` 生成三段式简报（无 AI 时降级为规则列表）；
  3. 存表 `digest`，`GET /api/digest/today` 给前端；
  4. 侧边栏加「简报」视图（`registerPluginView`）；
  5. 推送通道先做**邮件**（QQ 邮箱 SMTP + 授权码），后续可接企业微信群机器人 / OpenClaw。
- **不写代码的替代**：每天点「导出 CSV」或直接看日历页；但手机体验差。

#### P1 手机访问（不改 Briefdesk 代码）

- **问题**：Briefdesk 只监听 `localhost`，且中间件校验 Host 必须是 `localhost/127.0.0.1/::1`（`server/middleware.py:14,54-58`）→ 手机访问 `http://PC-IP:3000` 会返回 400。
- **方案**：本机跑 Caddy 反代，把 Host 重写成 `127.0.0.1:3000`、Origin 同步重写（这样同源校验也能过），再通过 **Tailscale**（免费、无公网暴露）访问：

```caddyfile
# C:\briefdesk\Caddyfile
:8080 {
    reverse_proxy 127.0.0.1:3000 {
        header_up Host 127.0.0.1:3000
        header_up Origin http://127.0.0.1:3000
    }
}
```

手机装 Tailscale 加入同一 tailnet → 访问 `http://<PC 的 Tailscale IP>:8080`。
**不要**把 3000 端口直接映射公网（无鉴权、聊天数据敏感）。

#### P2 待办 / 日历导出（.ics）

从 `/api/items` 的时间点生成 `.ics`，手机日历订阅；不做也行（日历插件已能在网页看）。

#### P2 手动收件箱插件（方案 B 的体验升级）

手机浏览器打开一个页面，粘贴文字 / 上传截图 → 直接进 Briefdesk 管道，省掉 QQ 中转。需要写一个新插件（SourcePlugin/WebPlugin，约 1–2 天），**非必需**。

#### P2 OpenClaw 心跳巡检

在 `HEARTBEAT.md` 加检查项：三个服务健康 + 最近同步时间 + 昨日卡片数；异常时让芙宁娜发微信 / QQ 提醒。你已有的 heartbeat 机制直接复用。

## 5.7 与班级工具站（tool.furina.fun）整合

**定位**：Briefdesk 是「本地加工厂」，工具站是「对外展示 / 协作窗口」。不把整段聊天推上公网，只同步**确认过的精选通知**。

### 5.7.1 工具站现状（已摸清）

| 项 | 值 |
|----|----|
| 代码 | `web/tools/index.html`（单文件、零依赖、原生 JS，五格切换：抽签/课表/作业/通知/体测） |
| 部署 | 阿里云 OSS Bucket `tool-furina-fun`，`deploy/sync_tools.py` 同步；`https://tool.furina.fun/` |
| 云端 | CloudBase PostgreSQL + PostgREST：`https://tool-d4gosudok46e0e081.api.tcloudbasegateway.com/v1/rdb/rest/` |
| 表 | `public.notices`（通知）、`public.homework`（作业）；前端用匿名 pub key + RLS，`archived=eq.false` 过滤 |
| notices 字段 | `id / title / body / pin / imp / author / owner / attachments(JSON，图片≤5MB 压缩、文件≤2MB、最多2个) / ts / archived` |

### 5.7.2 推荐整合方式（不动静态站架构）

```
Briefdesk（本地）→ 人工确认/精选 → 桥接脚本（采集机 Python，任意时段手动或定时）
   → POST {CloudBase}/notices（复用现有 pub key）→ tool.furina.fun 通知 tab 自动可见
```

1. **桥接脚本**：读 Briefdesk SQLite 里状态为「已确认/已收藏」的 items（或调 `/api/items`），映射成 notices 行后 POST；**只同步精选**，默认每天 ≤ 5 条。
2. **字段映射**（现有字段可先跑）：

| Briefdesk item | notices 现有字段 | 说明 |
|---|---|---|
| 标题 | `title` | 直接 |
| 摘要 + 原文要点 | `body` | 手工/生成的干净文案，不带群昵称 |
| 分类 | `body` 首行 `【分类】` 或新增列 `cat` | 建议新增列，见下 |
| 截止时间 | 正文注明 或 新增列 `deadline` | 同上 |
| 来源群 | `author` 填「简报台 · 来源：26信管1班群」 | 不暴露同学身份 |
| 原文/文档链接 | 正文 或 新增列 `link` | 公众号/腾讯文档可点 |
| 附件 | `attachments` | 复用现有 ≤2MB / 2 个限制 |

3. **建议新增 4 列**（**按红线，先征得你同意再改 CloudBase schema**）：`cat text`、`src text`、`deadline timestamptz`、`rich jsonb`（存公众号/小程序/腾讯文档卡片元数据）。不加列也能用，只是富媒体展示退化。
4. **反向**：工具站「发布通知」保持现状；Briefdesk **不反向拉取**，避免重复入库。
5. **可选的展示增强**：通知 tab 顶部加「来源：简报台」筛选与「今日简报」入口；这与示例页 `notice-demo.html` 的样式一致。

### 5.7.3 风险与边界

- notices 表是**公开可读**的（现有设计），所以只能放班级级、无个人隐私的通知；手机号/学号/身份证/宿舍号一律不入库。
- 匿名 pub key 本来就能写（现状如此），桥接脚本用同一把 key；不要额外暴露 Briefdesk 或聊天原文。
- 附件走现有 base64 方案，大文件别传；必要时只存链接。

## 5.8 同步发布到 QQ 频道

**目标**：同一份简报/通知，按板块同步到班级 QQ 频道，不重复搬运。

| 通知类别 | 频道板块 |
|---|---|
| 教务、团务、缴费、班级事务、重要通知 | **公告栏** |
| 作业、考试、课程资料 | **学习互助** |
| 讲座、志愿、文体活动 | **活动报名** |

**官方能力（QQ 频道机器人）**：
- 在 `bot.q.qq.com` 开放平台创建**频道机器人**（注意：和 OpenClaw 里那个 QQ 群 bot 是两套体系，别复用）；
- 频道主/管理员把机器人拉进频道，并授予目标子频道「发送消息」权限；
- 发布接口：`POST /channels/{channel_id}/messages`（带 `Authorization: Bot <token>`）；
- 频控：**主动消息默认每子频道 20 条/天**（可在频道设置里调整），每子频道 **1 秒 ≤ 5 条**；支持文本 / Markdown / 图片 / Ark。

**发布策略（推荐）**：
1. 每天最多 1 条「今日简报」+ 0–2 条重要单条通知，聚合为主，避免刷屏；
2. 格式：`标题` + `3 行摘要` + `截止时间` + `原链接`（工具站 / 公众号 / 腾讯文档）；
3. **AI 生成 → 你在示例页/简报台点「同步发布」→ 才发**，不自动发布；
4. 备选（零门槛）：生成「待发布文案」，手动粘贴到频道——先跑通流程，再上机器人自动化。

**待办**：申请频道机器人 → 记录 `guild_id` / 各板块 `channel_id` → 写约 100 行发布脚本 → 用示例页同款「板块选择 + 预览」交互。

## 5.9 富媒体通知适配（小程序 / 公众号 / 腾讯文档 / 文件 / 图片）

> 原则：**不追求 100% 还原微信卡片**，目标是「信息可读 + 入口可点 + 关键内容不丢」。示例页已演示所有形态。

| 类型 | 来源形态 | Briefdesk 现状 | 做法 | 展示 / 降级 |
|---|---|---|---|---|
| **公众号文章** | `<msg><appmsg>` XML（mmreader 多图文） | ✅ 已支持：`plugins/_common/article_parser.py` 拆条、卡片带 `article_url` | 直接用 | 标题 / 公众号 / 摘要 / 「打开原文」 |
| **小程序卡片** | appmsg XML（type 33/36：title/des/appid/path/thumb） | ❌ 无专门解析（会退化成 XML/占位） | 新增 enrich 阶段插件 `richcards`：解析 XML → 存 `rich` 元数据 | 卡片（图标/名称/描述/appid）+「复制路径 / 微信内打开」提示 + OCR/截图兜底 |
| **腾讯文档收集表** | 链接（`docs.qq.com/form` / `doc` / `sheet`） | ⚠️ 只当普通文字/链接 | URL 识别 + 卡片；收集进度需登录态，默认展示链接 + 截止时间 | 标题 / 收集人 / 截止 / 「打开收集表」；可一键加待办 |
| **QQ 群文件** | rich XML（`m_fileName` + `m_resid`，qqflow 已解析部分） | ✅ 文件名/大小 + 媒体代理 | 前端卡片 + 下载/打开 | 文件名 / 大小 / 打开（大文件只记链接） |
| **图片通知** | 截图（image） | ✅ OCR（需 `briefdesk[ocr]`） | OCR 文本入库 + 原图缩略 | 「OCR 已识别 N 字」+ 提取文字 |
| **通用链接** | 群内转发的网页 | ❌ | 白名单域名抓 `og:title/description`（防 SSRF，仅 `mp.weixin.qq.com`、`docs.qq.com` 等） | 链接卡片 |
| **语音 / 视频** | voice / video | ⚠️ 无下游 | 不转写（可选接 whisper） | 提示「需在原 App 查看」 |

**落地顺序**：P1 先把「公众号 + 图片 OCR + 腾讯文档链接」跑通（成本最低、收益最大）；P2 再做 `richcards` 插件覆盖小程序 / 文件 / 通用链接。

## 6. 部署与运维

### 6.1 主机与常开策略

- **主力 PC 即可**：微信 + QQ 常驻登录，Briefdesk + 两个 server 常驻。
- 电源计划：接通电源时「从不睡眠」；关闭硬盘休眠；屏幕可关。24/7 电费约 20–30 元/月。
- **可选**：二手迷你主机 / 旧笔记本专职采集（300–600 元），主 PC 可关机；但微信/QQ 多端登录、多机部署更复杂，**初期不建议**。

### 6.2 启动顺序（登录后自动）

1. 微信 / QQ（应用自带开机启动 + 自动登录）；
2. `weflow-server.exe --port 5033`（方案 A）；
3. `qqflow-server.exe --port 5032`；
4. Briefdesk（venv `python -m briefdesk`，cwd = `C:\briefdesk\app`）；
5. 看门狗（`pythonw.exe`，隐藏窗口，每 60s 健康检查）。

**计划任务**（用户态、登录触发；用 `pythonw` 承载避免黑框——沿用现有 gateway-watchdog 的经验）：

- 任务名 `BriefdeskStack`；动作 `pythonw.exe C:\briefdesk\scripts\watchdog.py`；
- 触发器：登录时 + 每 5 分钟；`StartWhenAvailable=true`。

### 6.3 看门狗与健康检查

| 检查 | 端点 | 判定 |
|------|------|------|
| qqflow-server | `http://127.0.0.1:5032/health` | 200 且账号 `ready` |
| weflow-server（A） | `http://127.0.0.1:5033/health` | 200 且账号 `ready` |
| Briefdesk | `http://127.0.0.1:3000/api/status` | 200 且 `lastSync` 距今 < 2h（有消息时） |

异常处理：重启对应进程 → 写日志 → 可选通知（OpenClaw 心跳 / 邮件）。

### 6.4 备份与恢复

- **每日 03:00** 调 `GET http://127.0.0.1:3000/api/backup` 下载 SQLite 到 `G:\Backup\briefdesk\YYYYMMDD.sqlite`，保留 14 天。
- 每周把 `.env` / `secrets\` / 配置备份到本地加密位置（**不要放公网网盘**）。
- 恢复：网页 `/api/restore` 上传 → 重启生效（原库自动保留 `.pre-restore`）。

### 6.5 升级与密钥轮换

- **锁版本**：weflow-server / qqflow-server 固定 v0.10.0；不自动升级。
- **微信/QQ 客户端自动更新建议关闭**；升级前先备份 keys，升级后验证；key 可能轮换。
- 微信重登 / 升级后若 Briefdesk 报「key 过期 / 图片坏」→ 重新提取 key → 更新钥匙串 → 重启。
- Briefdesk 升级：先备份 DB + 记录当前版本；升级后 smoke（`/api/status`、同步、分类各一次）。

### 6.6 排错速查

| 现象 | 原因 | 处置 |
|------|------|------|
| Briefdesk 显示「无消息源」 | `PLUGINS` 未启用 / 服务未启动 | 检查 `PLUGINS` 与 5032/5033 |
| 同步后 0 张卡片 | 会话没勾选 / `IGNORE_SELF` 把转发过滤了 | 勾选会话；收件箱场景设 `IGNORE_SELF=false` |
| qqflow 一直 503 | 账号没注册好 / 还在 indexing | 查 `/api/v1/accounts` 的 `state` |
| 注册 400 `invalid_key` | key 错 / 不是 16 字节 ASCII / 账号不匹配 | 重新提取 |
| 微信注册 400「页 1 HMAC 校验失败」 | key 错 / 不是该 wxid 的库 | 重新提取；确认 wxid 与目录 |
| 文本正常、图片坏 | 微信图片密钥缺失（A） | 补 `WEFLOW_IMG_AES_KEY` / `WEFLOW_IMG_XOR_KEY` |
| AI 分类报模型不存在 | 模型名/端点不对 | 用 Ollama 时确认 `qwen3:14b` 已 pull |
| qwen3 返回空 JSON | 思考模式吃光 token | `AI_REASONING_EFFORT=off` |
| 手机访问 400 Invalid Host | Briefdesk 的 Host 白名单 | 用 Caddy 反代重写 Host（§5.6） |
| 页面卡 / 分类慢 | 本地模型并发 1、批量回填大 | 降低 `BACKFILL_BATCH_MAX_COUNT`；或切云端 AI |
| qqflow 注册报 `unknown_qq` | `db_path` 留空且启动时 QQ 未登录 | 显式传 `db_path`，或先登录 QQ 再启动服务 |
| qqflow 找不到 token.txt | Briefdesk 插件注释过时 | token 在 Windows 凭据管理器，用 `qqflow-server token` 取 |
| QQ 群消息没进 Briefdesk | 会话未在「群聊筛选」启用；或 `BACKFILL_HOURS` 只覆盖 24h | 勾选群；首次设 `BACKFILL_HOURS=168` |
| QQ 服务 `state=error` | key 被轮换 / 库路径不对 / 解密失败 | 重新提取 key；核对 `db_path` 指向原始活库 |

## 7. 隐私、合规与风险

### 7.1 数据流向

```
本机聊天库（加密）→ 本机服务（只读解密）→ Briefdesk SQLite → AI（默认本机 Ollama）→ 浏览器
                                              │
                                              └─ 人工确认/精选 ─→ CloudBase notices ─→ tool.furina.fun 通知板块（同学可见）
                                                                  └─ 可选 ─→ QQ 频道公告栏 / 学习互助 / 活动报名
```

**离开本机的只有**：
1. 切云端 AI 时，**脱敏后**的消息正文（手机号/身份证/邮箱会打码，姓名/群名不会）；
2. **精选通知的标题/摘要/链接** → 公开的工具站通知板块（班级可见，不含原始聊天记录与个人信息）；
3. **每日简报/重要通知** → QQ 频道对应板块（需人工点「同步发布」）；
4. 推送出去的邮件简报文本；手机访问时的内网 / Tailscale 流量（不出公网）。

### 7.2 群公告模板（发到班级群 / 收件群）

> 同学们好，我在做一个班级通知汇总的小工具，会把本群和我收到的班级通知整理成一份**本地简报**，只用于我自己的班级事务提醒，**不外传、不公开、不用于任何商业用途**。如果不想自己的发言被收录，请私聊告诉我，我会把它排除。

### 7.3 风险清单

| 风险 | 概率 | 影响 | 对策 |
|------|:---:|------|------|
| 微信 key 提取失败 / 工具不兼容 4.1.15.13 | 中 | 方案 A 搁浅 | 时间盒 30 分钟，失败立即转方案 B |
| 微信升级 / 重登导致 key 轮换 | 中 | 微信采集断 | 重新提取；或长期用方案 B |
| PC 关机 / 掉线 / 微信 QQ 退出 | 中 | 漏采窗口期消息 | 常开 + 看门狗 + 重要通知班委转发兜底 |
| 微信 / QQ 风控 | 低 | 账号异常 | 只读、不自动发言、不用协议端、尽量用小号 |
| 服务停止 / 端口冲突 | 低 | 采集断 | 看门狗 + 告警 |
| AI 误分类 / 漏收录 | 中 | 漏重要通知 | 每日简报人工过目 + 手动改分类 + 关键类别调提示词 |
| 数据泄露 | 低 | 隐私 | 不公网暴露；手机走 Tailscale；备份加密；密钥进钥匙串 |
| 上游仓库停更 / 兼容性退化 | 中 | 升级即坏 | 锁版本 + 保留人工兜底路径 |
| DB key / API token 泄露 | 低 | 他人可读本机聊天 | 不写 `.env` / 不贴聊天 / 文件 ACL |
| 本机端口被误暴露 | 低 | **token 泄露 = 全部聊天记录泄露**（qqflow 无会话级 ACL，只要 token 就能读该账号全部会话） | 保持默认 `127.0.0.1`；防火墙限制；不装反代到公网 |
| 工具站公开通知泄露个人信息 | 中 | 同学隐私 | 只发精选、去标识；证件照/名单类不上公网；同步前人工过目 |
| QQ 频道误发 / 刷屏 | 低 | 打扰同学、显得不专业 | 人工确认后再发；每日上限（1 条简报 + ≤2 条重要）；板块映射固定 |
| CloudBase 增列 / 桥接脚本出错 | 低 | 通知板块异常 | 改 schema 前备份；只增列不删列；桥接脚本先 dry-run |
| 富媒体解析随微信/QQ 更新失效 | 中 | 卡片降级 | 统一降级为「原文/截图 + 链接」，不阻断主流程 |

### 7.4 红线

- 只解密**自己的**数据；不导出、不传播他人聊天内容。
- 不把服务暴露公网；不把 token / key 写进仓库、聊天、截图。
- 不做自动回复 / 群发 / 抢红包等任何**写操作**。

## 10. 需要你拍板的 7 件事

1. **微信侧**：先花 30 分钟试方案 A 的 key 提取，还是直接走方案 B（纯人工转发）？→ **建议先试**，失败立即转 B。
