# 存储盘点：通知附件 / PPT 到底存在哪（2026-11-10 只读实测）

> 回答「目前上传上去的通知附件、PPT 等是存在云服务器中吗」。
> 方法：OSS 只读列举（`tool-furina-fun`）+ CloudBase PostgREST 管理员 token 只读 GET（只取聚合，不落正文/个人信息）+ 本机 `C:\briefdesk\data` 目录统计。
> 结论一句话：**通知附件在腾讯云 CloudBase 的 PostgreSQL 里（base64 内嵌），PPT 媒体在阿里云 OSS 香港；两者都不在 ECS 上。**

## 1. 通知附件：在腾讯云 CloudBase 数据库里（不在 ECS/OSS）

| 项 | 实测（2026-11-10 18:2x） |
|---|---|
| 位置 | `public.notices.body`（PostgreSQL，腾讯云 CloudBase 上海） |
| 通知行数 | 93 行（`archived=false`） |
| body 总字节 | **8.05 MB** |
| 内嵌 `data:` URI | **41 个，base64 共 7.89 MB（占 98.0%）** |
| 类型分布 | image/jpeg 4.47 MB、application/pdf 2.53 MB、docx 0.82 MB、xlsx 0.05 MB、xls 0.03 MB |
| 字段分布 | `items[].src` 4.48 MB（图片直显）、`items[].url` 3.32 MB（文件）、`items[].archive.files[].url` 0.08 MB |
| 本地原件 | `C:\briefdesk\data\qq-files`（30 文件/11.8 MB）、`images`（40/7.0 MB）、`wechat-media`（3/4.2 MB）、`archive-files`（3/0.1 MB） |
| 作业附件 | `public.homework.attachments` 合计 0.22 MB，当前无 base64 片段 |

影响：网页/小程序每次通知签名变化都要整表拉取 → 8 MB 级 JSON；这是「通知页慢/费流量」的最大原因。
外置后（附件改 URL）预计 body 降到 ~0.15 MB 级（去掉 data URI 后本地实测 0.15 MB / gzip 0.04 MB）。

## 2. PPT：元数据在 CloudBase，媒体在阿里云 OSS 香港（当前为空）

| 项 | 实测 |
|---|---|
| 元数据 | `public.ppt_decks` 20 行，**全部 `deleted=true` 的测试数据、0 个 ready**；`ppt_upload_chunks` 0 行 |
| 媒体设计位置 | 阿里云 OSS `tool-furina-fun`（oss-cn-hongkong），**公共读**，路径 `ppt/a/<deckId>/<buildId>/`（WebP 主图/缩略图/MP4）+ `ppt/src/<deckId>/source.<ext>` |
| 实测对象 | `ppt/` 前缀 **0 个对象**；整个 bucket 仅 6 个对象 / 0.78 MB（站点文件本体） |
| 访问方式 | 直连 `https://tool-furina-fun.oss-cn-hongkong.aliyuncs.com/...`（不依赖暂停中的 `tool.furina.fun`） |

影响：PPT 媒体若真的上传，会走**香港 OSS 跨境链路**（实测主线香港 OSS 握手 2–4 秒），首次加载会慢；
但 PPT 资产设计为 immutable 长缓存，第二次起浏览器缓存命中。后续可加 ECS 反代 + 磁盘缓存优化。

## 4. 结论对迁移的影响

- **② 通知附件外置**：要搬的不是「ECS 上的文件」，而是 CloudBase 里的 7.89 MB base64；需要定存储（ECS 本地磁盘 / 私有 OSS）+ 鉴权（班级 token / 签名 URL），并改本机同步管线 + 前端渲染（小程序/安卓需发版）。
- **PPT**：媒体本来就在阿里云 OSS（不在 ECS），且当前为空；小程序侧还需在微信后台把 OSS 域名加入 request/downloadFile 合法域名。
- **ECS 目前没有任何班级数据**（只有站点静态文件 + 班级简报 board 副本）；删 ECS 不会影响云端数据。
