## 2. 校级差距：从“70 人一个班”到“约 1.5–2 万人、13 学院（部）、350–450 个行政班”

规模假设（【外部事实】+【推断】）：学校全日制在校生 16,000 余人（含研究生 3,100 余人，官网简介数据截至 2026-05）；13 个学院（部）、19 个本科专业（2024 审核评估口径）。按本科约 12,900 人、每班 28–37 人估算 → **行政班 350–450 个**（置信：中，需以教务处实际班级为准）。

| 差距维度 | 现状 | 校级要求 | 缺口等级 |
|---|---|---|---|
| 班级/学院层级 | 无任何层级；`class_ids` 单表、无 `school/college/class` | 学校→学院（13）→专业→年级→班级；名单可继承/覆盖 | **P0** |
| 角色模型 | 管理员 0/1 布尔；班委=role/badge 字符串；团员=名单表 | 学生/班委/团支书/辅导员（只读+汇总）/教师/学院管理员/校级管理员；权限按作用域 | **P0** |

### 2.1 容量瓶颈的硬证据

- **通知全量拉取**：`notices?select=*&order=ts.asc` 一次性整表（`tools/index.html:3622`），现有可见 104 条正文合计 13.3MB（表 36MB，单条最大 2.0MB、43 条含 data URI）`_audit/cloudbase_data_audit_20261111.md:15`；签名变化才整表重拉（`:3617`，约 2KB 签名）——单班尚可，多班全校不可行。
- **附件外置能力已就绪但默认关闭**：ECS `/att` 签名 URL 服务已上线、`NOTICE_ATTACH_EXTERNALIZE` 默认关（`AGENTS.md §21-②`）；去 data URI 后通知接口体积 5.93MB→0.15MB（`_audit/班级工具站_服务配置盘点_2026-11-09.md:194-195`）。
- **RLS 逐行函数**：策略大量调用 `auth_ok()/auth_sid()/auth_admin()`（如 `power.sql:60,64,68`；`2026-11-11_stage_prefs.sql:48-56`）。`auth_sid()` 每次校验 `private.class_sessions`（`deploy/cloudbase/2026-11-11_stage_rpc.sql:20-22,53-54`）。【推断】不随行变化的谓词大概率被 PG 以 one-time filter 优化，但**混合行条件的策略（`seat=auth_acc()`）逐行求值**；且全表无 `class_id` 索引，5k+ 用户时 `notices/visits` 顺序扫描会显著放大延迟（置信：中）。
- **索引缺失**：`deploy/cloudbase/` 全部迁移中未见 `visits` 索引，而统计页按 `slot>=` 取 2,000 行（`tools/index.html:10661`）——`visits` 年增百万行后必成慢查询（事实：无索引；推断：需补）。
- **会话表增长**：`private.class_sessions` 2,091 行/70 人/约 6 周（`_audit/cloudbase_data_audit_20261111.md:16,37`），按 8,000 DAU 外推约 1.2M 行/年（推断，中等置信）。
- **个人版配额**：CloudBase 个人版 40,000 资源点/月，腾讯云公开换算“≈200 万次数据库调用/月、4GB 容量”（外部，营销口径，置信中）；当前单班 70 人已接近“班级级无感”，全校请求量将超 10 倍以上（见 §5）。

## 3. 至少 3 个技术方案与改造量

> 人日口径：1 人日≈6–8h；单人开发 + AI 辅助；含自测，不含独立验收（+1 人日）与合规评审（+0.5–1 人日）；置信度：中（除注明外）。

### 3.1 方案 A：每班/每学院独立实例（复制环境或环境模板）

**做法**：一个班（或一个学院）一套 CloudBase 环境 + 一套前端配置（`var CB`/`CBK` 运行时可注入）+ 独立名单/管理员；本机管线按实例各跑一份。
**优点**：代码改动最小；数据隔离最彻底（物理隔离）；单班故障不扩散；回滚=切回旧环境。
**缺点/风险**：环境创建、CORS、密钥、云函数触发器、到期续费**全部人工**（当前 DDL/RLS 不在仓库 → 新环境无法自动化重建，P0）；无跨班汇总/通知；管理员权限=环境级，难以交给学生干部；成本随班数线性（约 ¥240/年/环境量级，需确认当前套餐价）；与 AGENTS.md“不得引入构建链”冲突（每班前端配置需构建/或运行时外部 JSON，得加配置层）。
**回滚**：DNS/前端指回原环境即可；数据不迁移。
**改造量**：一次性工程 6–8 人日（运行时配置注入 + 环境模板脚本 + 迁移手册）+ **每新增一班 3–5 人日** + 每班每年运维 1–2 人日。10 班 ≈ 36–58 人日；**全校 350–450 班 ≈ 1,000+ 人日（不可行）**。

### 3.2 方案 B：单环境多租户（新增学校/学院/班级维度 + RLS 重写 + 角色体系）

**做法**：保留 CloudBase PG/PostgREST；新增目录表 `schools/colleges/classes/class_members`（或把 `private.class_ids` 扩为成员表）；所有共享表加 `class_id`（学院级资源加 `college_id`）；RLS 由 `auth_ok()` 改为“作用域校验”（`auth_in_class(class_id)` / 管理员作用域）；新增辅导员/教师/学院/校级管理员角色与只读汇总视图；新表：`audit_log`、`import_jobs`、`token_sessions`（可吊销/刷新）；通知 audience 扩展 `class/college/school`；前端加“班级/学院切换 + 名单导入 + 分级管理”；小程序/安卓同步。
**优点**：一套环境、一份运维；跨班汇总天然可行；数据仍走现有 RLS/PostgREST 模式（团队最熟）；渐进式，可先只做 1 学院。
**缺点/风险**：**改造最重的是 RLS**（全部共享表约 10 张 × 读写策略 × 新旧兼容），写错即跨班越权；线上 RLS 不在仓库（`_audit/cloudbase.md:161`、`_compliance/audit_current_state.md:324-332`），没有权威基线可 diff；一次性大迁移需要**冻结期**；单环境故障=全校故障。
**回滚**：数据迁移前全量快照；RLS 策略保留旧定义按版本切换（`pg_policies` 导出）；前端按 `APP_VER` 灰度；最坏回滚=恢复快照 + 旧前端。
**改造量**：**51–74 人日**（DB 10–14 / Web 12–18 / 小程序 10–14 / 安卓 8–12 / 运维与数据迁移 5–8 / 测试 6–8）；**MVP 子集 18–28 人日（仅 Web；三端同步 22–36）**（见 §4）。

### 3.3 方案 C：重写/重构后端并对接学校统一身份认证（authserver）+ 现有系统

**做法**：自建业务后端（ECS / 云托管 / 校内托管）+ PostgreSQL 正规 schema（学生、班级、学院、角色、审计、通知、作业、投票…），三端改调自有 REST API；身份对接学校统一认证（`jwxt/jwxt.py:66` `https://authserver.fjtcm.edu.cn`，jwxt 已实测纯 requests 完成 SSO `jwxt/jwxt.py:428-438`）；可选对接教务课表/成绩、学工名单。
**优点**：真正的校级架构：统一身份、分级权限、审计、可横向扩展、可迁移校内；摆脱 CloudBase 个人版到期/配额；三端可共享一套 API 契约。
**缺点/风险**：**依赖学校授权**（CAS/OAuth 客户端注册、回调域名、可能要求校内托管/等保/数据不出校）——周期与结果不可控（置信低）；备案/域名（小程序域名必须 ICP 备案，见 §9）；工作量最大；唯一开发者难以长期运维“正式系统”；现有功能需全部重写/回归。
**回滚**：并行运行（旧 CloudBase 链路保留开关），按班级灰度切换；数据双写/回灌需设计。
**改造量**：**66–101 人日**（后端 15–22 / DB 5–8 / SSO 5–10 / Web 10–15 / 小程序 10–14 / 安卓 8–12 / 运维监控 6–10 / 测试 6–8），不含学校审批等待与合规评估。

## 4. 最小可行校级版（MVP）范围建议

**目标**：验证“多班 + 分级角色 + 名单导入 + 数据隔离”成立，成本可控、可回滚。**建议试点=用户所在学院或同年级 4–10 个班、约 150–350 人。**

做：
1. **目录与名单**：学院/班级/成员表；管理员导入 CSV（教务/学工导出）→ 自动生成班级；支持转专业/休学标记；名单不导出学号到公开页。
2. **身份**：沿用“学号+姓名+token”（与学校统一认证解耦，避免审批阻塞），但 token 缩短为 7 天 + 静默续期 + 管理员吊销；加登录失败限流。
3. **数据隔离**：仅先改造“通知/作业/名单/课表”四类共享表加 `class_id` + 作用域 RLS；其余表（PPT/大屏/抽签存证/体测）**暂不校级化**。
4. **角色**：班级管理员（班委）、学院管理员（用户本人/辅导员只读）。学生默认只见本班。
5. **跨班汇总**：学院管理员可看各班通知/作业完成率汇总（只读，不合并学生个人明细）。
6. **通知附件外置**（前置条件，否则容量/带宽不达标）：先启用 ECS `/att` 签名 URL。
7. **审计**：管理员登录、导入、角色变更、跨班查看四类事件落 `audit_log`（保留 180 天）。
8. **运维**：数据库快照 + 恢复演练 1 次；CloudBase 续费/迁移方案在启动前拍板。

明确不做（本期）：
- 不做全校 350–450 班全量迁移；不做多校 SaaS。
- 不改小程序主体、不做学校统一认证 SSO（留给 v2/方案 C）。
- 不校级化：PPT 转换/大屏/抽签存证/投票/水量/电费（保持班级级）；不做教师端成绩/考勤。
- 不做安卓正式版分发；不做微信支付/任何收费。
- 不做全校通知即时推送（维持 30s 轮询）；不承诺 DR/多活。

## 5. 容量估算（1k / 5k / 20k 用户）

### 5.1 假设（全部为估算依据，需以真实埋点校准）

- 用户数→班级数：按 32 人/班 → 1k≈31 班，5k≈156 班，20k≈625 班（20k 为“全校+教职工/研究生/家长上限”，学校实际全日制约 16k）。
- DAU = 40% 注册用户（当前单班可能 50–70%，校级取保守 40%）；日活中 10% 同时在线为峰值。
- 人均请求 150 次/日（前端 30s 轮询 `tools/index.html:12152`，TTL 门控 2–10 分钟 `:4978`；实际 60–200，需埋点确认）。
- 页面 1.23MB，gzip 约 0.35–0.40MB（按 `AGENTS.md §21` 32.5% 压缩率推算）。
- 通知：现状单班 36MB/135 行；**外置附件后**按 0.15MB 全量/班 + 每班 135 行/年；未外置按 13.3MB/班可见正文计。
- 行大小：`userdata` 8–15KB/人（v6 blob：`AGENTS.md §4b-5`）；`marks` 80B/行；`visits` 70B/行；`poll_votes` 60B/行。
- CloudBase 个人版：40,000 资源点/月 ≈ 200 万次 DB 调用/月、4GB 容量（外部，营销换算口径，置信中）。**实际配额以控制台/账单校准（需确认）**。

### 5.2 三档估算表

| 指标 | 1,000 用户（约 1 学院） | 5,000 用户（约 3–5 学院） | 20,000 用户（全校上限） |
|---|---|---|---|
| DAU（40%） | 400 | 2,000 | 8,000 |
| 日请求（150/DAU） | 60,000 | 300,000 | 1,200,000 |
| **月请求** | **1.8M**（个人版配额约 90%） | **9.0M**（个人版 4.5×，需标准版） | **36M**（个人版 18×，标准版约 2.2×，需企业版/自建） |
| `userdata` 行/容量 | 1k / ~10MB | 5k / ~50MB | 20k / ~200MB |
| `marks` 年增 | 20k 行 / ~2MB | 100k 行 / ~10MB | 400k 行 / ~40MB |
| `visits` 年增 | 0.22M 行 / ~15MB | 1.1M 行 / ~80MB | 4.4M 行 / ~310MB（**无索引，必加**） |
| `notices` 行/容量 | 4k 行 / 外置 0.6MB·正文 | 20k 行 / 3MB | 54k 行 / 8MB |
| `notices` 内嵌附件（若不外置） | ~0.4GB | ~2GB（接近 4GB 上限） | **~5.3GB（超个人版容量）** |
| DB 总量（外置后，1 年） | 42MB + 0.2–0.5GB | 0.5–1.2GB | 2–4GB |
| 日静态出网 | ~0.14GB | ~0.7GB | ~2.8GB |
| 日通知出网（外置） | 0.12GB | 0.6GB | 2.4GB |
| 峰值并发 / QPS | 40 / 2–4 | 200 / ~10 | 800 / ~30–40 |
| 结论 | **个人版临界**：必须续费+附件外置+会话清理 | **需升套餐**+索引+分页+备份 | **当前形态不可行**：需重写/分环境/校内托管+RDS |

### 5.3 容量结论

1. **1k 用户是当前架构的“天花板附近”**：月请求已占个人版配额约 90%，附件不外置时单次通知拉取 13–36MB，4G 弱网不可接受（与 `_audit/班级工具站_服务配置盘点_2026-11-09.md:199-206,244` 结论一致）。
2. **5k 用户必须三件事同时做**：升级 CloudBase 套餐、附件外置、`visits/notices` 补索引与分页；否则 DB 容量与慢查询先崩。
3. **20k 用户需换形态**：不是“加钱就行”——单 PostgREST 环境、无 `class_id` 分区、单 ECS 5Mbps、本机单点管线都会成为硬瓶颈；应走方案 C 或“按学院多环境 + 校内托管”。
4. **未计入**：PPT 演示（单 deck 兼容版 39MB 存量，`AGENTS.md §23-⑦`）与 OSS 存储/流量；校级化 PPT 需单独容量预算（OSS 15–40GB/年，推断）。
5. **置信度**：行数/容量=中；请求配额换算=中低（腾讯云营销口径，须账单校准）；DAU/人均请求=低–中（需真实埋点）。

## 6. 技术可行性结论、前置条件与 Top5 风险

**结论：有条件可行（Conditionally Feasible）。**
- ✅ MVP（1 学院内 4–10 班、约 150–350 人）：**可行**，现有技术栈可承载，仅 Web 18–28 人日（三端同步 22–36）+ 运维。
- ⚠️ 全校（16k 人/350–450 班）：**当前形态不可行**；需方案 B 完整落地（51–74 人日）或方案 C（66–101 人日 + 学校支持），且必须先完成 §6.1 前置条件。

### 6.1 前置条件（全部满足才可立项）

1. **CloudBase 续费/迁移决策**：2026-12-10 到期，无备份/DR 演练（`_audit/cloudbase_data_audit_20261111.md:13,60-62`）。
2. **导出权威 schema 入库**：`class_verify`、`private.class_sessions`、`auth_*`、homework/notices 现行 RLS 均不在仓库（`_compliance/audit_current_state.md:324-332`）——**否则新环境无法重建、迁移无法审计**。
3. **组织授权与合规**：学院/学校同意；学生名单（学号+姓名）处理告知/同意；教师查看范围；PIPL/数据保留/删除权；小程序主体与发布方式确认。
4. **备案与 HTTPS**：小程序服务器域名必须 ICP 备案、HTTPS、不能用 IP/父域名（外部事实，§9）；当前域名备案暂停、临时 `ko-link.cn`（`AGENTS.md §0-8`）。
5. **附件外置 + 容量套餐**：先启用 ECS `/att`，再评估 CloudBase 套餐档位。
6. **角色模型拍板**：辅导员/教师/学院管理员能看什么（只读？跨班？是否看学号？）——这是产品决策，直接决定 RLS 复杂度。
7. **运维保障**：唯一开发者之外的备份/续费/证书责任人；至少“双人知情”的操作手册。

## 7. AGENTS.md「单文件零依赖、不得引入构建链」红线评估

**背景**：该红线是**班级级阶段用户明确要求**（`AGENTS.md §0-2`：“禁止 npm/vite/TS/框架，产物必须双击可开”）。它带来了零运维部署、无供应链风险、离线可用、OSS 直传即可上线等真实收益。

**校级推广下是否成为工程瓶颈？——分阶段回答（【推断】，置信中）：**

| 规模 | 判定 | 理由 |
|---|---|---|
| 70 人（现状） | 合理 | 单人、单班、无构建链=部署 1 次上传，收益最大 |
| 300–1,000 人（MVP） | **不是硬阻塞** | 单文件仍可管理；但需把“每班配置/角色/名单”外置为运行时 JSON（否则文件继续膨胀）；19k 行 + 100+ 测试脚本已接近单人维护上限 |
| 5k–20k（全校） | **会成为瓶颈** | ①每次小改全量发布 1.23MB（gzip ~0.35MB）给全部用户，无法按班级/功能分包懒加载；②多租户/多角色代码会再加 3–5k 行，单 IIFE 全局作用域导致耦合与回归风险陡增；③无类型/无模块边界，多人协作（含接手者）几乎不可行；④三端（web/mp/android）重复实现放大了这个问题；⑤按班配置若继续硬编码在文件里，改一个学院要重发全站 |

**建议（需用户重新拍板，不是研究员单方面推翻红线）**：
1. **保留**“零依赖、无运行时 npm、产物可直接静态托管”的内核（这是可迁移的资产）。
2. **放宽**“单文件”到“单文件 + 1 个运行时配置 JSON”（或 `config.js`），至少把班级/学院/角色/工具开关从代码中移出。
3. **可选放宽**“不得引入构建链”为“允许**离线构建**、产物仍是静态 HTML”（例如用简单打包把 3–5 个源文件合成单文件）。若用户坚持零构建，则必须在单文件内建立**显式模块边界 + 更严格的自动化回归**，并接受“校级版只做 B 的最小集、不追求长期演进”。
4. 量化代价：校级化后预计 `index.html` 增至 1.6–1.9MB（gzip ~0.45–0.55MB），首屏在 4G 下 +0.5–1s；测试脚本从 100+ 增至 150+，每次发版回归时长显著上升（推断）。
5. **结论：需要用户重新决策**——固定“单文件零构建”与“全校多班长期维护”两者不可兼得；建议以 MVP 为界，MVP 后做一次技术栈决策（保留单文件 vs 允许离线构建）。
