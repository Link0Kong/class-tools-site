## 5. 如果以后要把服务收拢到阿里云 ECS，哪些能搬 / 哪些搬不了

**能搬、且备案通过后本来就要搬：**
1. **网页静态站**：把最新 `index.html`/`tt.json`/assets 用 nginx（或 Caddy）放到 ECS，启用 443 + HSTS，`tool` 记录从 OSS 香港切成 A → `121.196.47.2`（这就是 ICP 备案通过后的正常路径，备案资源本来就是这台 ECS）。
2. **班级简报 board + 同步 API**：已经在 ECS 上，只需补 HTTPS 和定时更新静态站镜像。

**可以搬但成本不低（要看 CloudBase 续费 vs 自建）：**
3. **CloudBase 后端**：PostgreSQL 可以自建在 ECS（2C2G 能跑），但需要把 18+4 张表、RLS、`class_verify`/`auth_*`、整套 PostgREST 网关重建；三端要改 base URL；小程序 request 域名必须换成**已备案的自定义域名**（IP 不行）。工作量以人日计，且要等备案。
4. **云函数定时任务**（电费/英语作业/健康巡检）：纯公网 HTTP，可改成 ECS 上的 cron 脚本；但电费/英语作业本机已有兜底。

**搬不了（不要把时间花在这上面）：**
5. QQ/微信消息采集（本机客户端 + 本地库 + 密钥）、附件/OCR、教务抓取（校园内网）、作业整理的 Edge 登录态——这些天然依赖这台 Windows 电脑，除非改成「本机只上传原始消息、云上分析」的架构。
6. 微信小程序前端、安卓 App 分发——属于微信平台/应用市场，不在任何服务器。
7. DeepSeek AI、完美校园、班级小管家、学校教务、Let's Encrypt——第三方服务，只能调用。

**推荐顺序**：备案通过 → 逐条恢复 DNS（tool 指 ECS，其它记录按需清理）→ ECS 部署最新站 + HTTPS → 观察稳定 → 再决定 CloudBase 续费还是迁 ECS（不要先停 CloudBase）。

## 6. 追加：现有 ECS 配置够不够迁移（2026-11-09 深夜补测）

### 6.1 实测规格与当前负载

| 项 | 实测值 | 来源 |
|---|---|---|
| CPU / 内存 | 2 vCPU / 2 GiB | ECS DescribeInstances |
| 系统盘 | **40 GB** ESSD Entry（cloud_essd_entry） | DescribeDisks |
| 公网带宽 | **出峰值 5 Mbps**、入 200 Mbps，**按使用流量计费（PayByTraffic）** | DescribeInstanceAttribute |
| 近 7 天实际负载 | CPU **avg 3.0% / p95 3% / max 5%**（146 个 1h 采样点）；出网流量接近 0 | ECS DescribeInstanceMonitorData |
| 当前在跑 | Caddy + briefdesk-board（+ 旧静态镜像） | 上一节 |

> 云监控 CMS 指标接口从本机不可达（`cms.aliyuncs.com` 连接失败），改用 ECS 自带 `DescribeInstanceMonitorData`（只读）取到 CPU/流量。

### 6.2 迁移对象的真实用量（决定配置的核心数字）

| 对象 | 体积 | 说明 |
|---|---|---|
| 网页 `index.html` | 799,206 B；**gzip 后 238 KB** | 单人首屏主要成本 |
| 通知数据（`notices?select=*`） | **5.93 MB**（gzip 3.95 MB） | 68 组紧凑 payload；**97.5% 是 37 个内嵌附件 data URI** |
| 通知数据（去掉 data URI 后） | **0.15 MB**（gzip 0.04 MB） | 若附件改 OSS URL，接口体积降 40 倍 |
| 数据库现有数据量 | 通知 body ≈6 MB + 其它表（power/power_history/userdata/marks/…）几 MB 级 | 当前 <100 MB，40 GB 盘绰绰有余 |
| 云函数替代（cron 脚本） | 单次 <10 s、瞬时内存 <200 MB | power/xgj/health 三个任务 |

### 6.3 带宽测算（5 Mbps = 0.625 MB/s）

| 场景 | 单人耗时 | 10 人并发（不压缩上限） | 结论 |
|---|---|---|---|
| 静态站（gzip 238 KB） | ≈0.4 s | ≈4 s | 可接受 |
| 通知接口 **未优化**（gzip 3.95 MB） | ≈6.3 s | ≈63 s | **不可接受** |
| 通知接口 **附件外置后**（gzip 0.04 MB） | ≈0.06 s | ≈0.6 s | 可接受 |

### 6.4 结论（按迁移范围）

| 迁移范围 | 够不够 | 说明 |
|---|---|---|
| ① 只迁「静态站 + 简报 board + 小 API」，后端继续 CloudBase | ✅ **够，且富余** | 当前 CPU 3%、出网近 0；5 Mbps 对 gzip 后的静态站足够；补 HTTPS/443 即可 |
| ② 连 CloudBase 后端（PostgreSQL + PostgREST + 定时任务）一起迁 | ⚠️ **CPU/磁盘够；内存 2 GB 是最低线；5 Mbps 带宽不够** | 内存：系统+Caddy+uvicorn ~0.5 GB，加 PG ~0.4–0.6 GB、PostgREST ~50 MB、cron 瞬时 ~200 MB → 峰值 1.2–1.6 GB，建议 +2 GB swap 或升 2C4G；带宽：必须先做「附件 data URI → OSS URL」或提高出峰值，否则通知页并发会卡到 60 s+ |
| ③ 把本机采集/AI/OCR/教务/浏览器自动化也搬上去 | ❌ **不够也不该** | 依赖本机 QQ/微信客户端、校园内网、本机 Edge 登录态与二进制；2C2G 也跑不动 Edge/OCR |

### 6.5 若决定迁移，建议的最小改动

1. **通知附件外置**（收益最大）：通知 body 里的 `data:` URI 改为 OSS URL / 独立接口，接口体积 5.93 MB → 0.15 MB。
2. **调高出峰值带宽**：当前已是按流量计费，把 5 Mbps 峰值调到 50–100 Mbps 不改变计费方式，只按实际流量付费（杭州约 ¥0.8/GB；粗略估算 70 人×每天 2 次×5.93 MB ≈ 25 GB/月 ≈ ¥20/月，优化后 <¥2/月）。
3. **内存**：加 2 GB swap（40 GB 盘够用）；PostgreSQL `shared_buffers` 128–256 MB；有预算升 2C4G 最稳。
4. **HTTPS**：Caddy 自动证书 + 443 监听（安全组已放行）；备案通过后 `tool` 记录切 A → 121.196.47.2。
5. **磁盘**：40 GB 当前够；预留约 20 GB 给数据库备份/日志；长期附件放 OSS，不要长在系统盘。

> 成本对比（粗）：CloudBase 个人版续费约 ¥239/年（估算）；ECS 已付到 2027-11-03，迁移只省这笔订阅费，但要自己承担数据库备份、证书续期、系统安全更新等运维。**省钱不是主要理由，数据自主/架构可控才是。**

## 7. 迁移对使用体验的影响（2026-11-09 夜间实测评估）

实测环境：福州电信家庭宽带（出口 110.88.100.15），2026-11-09 22:40–22:55，`curl` 多轮独立连接；手机 4G/5G 的绝对值会不同，但「香港 vs 内地」的方向性差异可参考。

| 目标 | connect | TLS | TTFB | 说明 |
|---|---|---|---|---|
| **阿里云 OSS 香港**（23 B 小对象，HTTPS） | 1.36–2.41 s | **2.06–3.79 s** | **2.41–4.14 s** | 即使只取 23 字节，握手也要 2–4 秒 |
| 阿里云 OSS 香港（23 B，HTTP 明文） | 0.36–1.37 s | — | 0.71–1.72 s | 换 HTTP 也仍有 0.7–1.7 s 延迟 |
| 阿里云 OSS 香港（`index.html` 732 KB，HTTPS） | 0.4–3.4 s | 1.2–6.1 s | 2.0–6.5 s | 三次总耗时 **7.1 / 20.0 / 15.3 s** |
| **阿里云杭州 ECS**（`/` 旧站 167 KB，HTTP） | 0.02–0.03 s | — | 0.04–0.05 s | 总耗时 **0.09–0.17 s** |
| **腾讯云 CloudBase 上海**（网关根，218 B） | 0.02–0.05 s | 0.05–0.08 s | 0.08–0.12 s | 后端延迟已经很快 |

### 7.1 结论：迁移的体验收益，来自「香港 → 内地入口」，不是「CloudBase → ECS」

| 迁移内容 | 对使用体验的影响 | 量级 |
|---|---|---|
| **网页静态站从香港 OSS 搬到内地 ECS**（备案通过后） | ⭐⭐⭐ 明显提升：消除跨境 2–4 秒握手与多秒下载；配合 gzip（799 KB → 238 KB）首屏可到亚秒级 | 首屏 7–20 s → 0.4–1 s（单人、5 Mbps） |
| **通知附件外置**（`data:` URI → OSS/独立 URL） | ⭐⭐⭐ 最大体感提升：新通知时才全量拉取，5.93 MB → 0.15 MB | 每次刷新省约 5.8 MB / 4G 下省 2–5 s |
| **同源 API + gzip/HTTP2/缓存头**（后端也在 ECS 时才有） | ⭐ 小幅提升：每请求省 50–80 ms，整页 6–8 个请求累计 0.3–0.6 s | 中 |
| **CloudBase 后端迁 ECS（其余不变）** | ➖ 几乎无感；反而增加单机风险（CloudBase+OSS 是两套托管服务） | 低/负 |
| **小程序 / 安卓** | ➖ 基本无感（现在走 CloudBase，网关 80–120 ms 已很快；迁移后换 api 域名延迟相近） | 无 |
| **稳定性** | ⚠️ 变差：单台 ECS 挂 = 全站挂；CloudBase 到期虽是风险，但续费后仍是托管高可用 | 负 |

> 一句话：**为了「网页秒开」值得把静态站搬内地；为了「体验」去全量迁后端不值得。** 附件外置和 gzip 是最高性价比的两步，且大部分不依赖迁移。

### 7.2 体验维度的行动优先级

1. 备案通过 → 静态站部署到 ECS + HTTPS + gzip（恢复访问 + 消除跨境延迟）。
2. 通知附件外置（5.93 MB → 0.15 MB）——即使后端暂留 CloudBase 也建议先做。
3. 缓存头/HTTP2/同源优化（迁移时顺手做）。
4. 后端是否迁：按「数据自主 / 费用」决策，不要按体验决策。
