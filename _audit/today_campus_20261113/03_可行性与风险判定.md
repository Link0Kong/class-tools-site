## 0. 结论摘要（可决策版）

**一句话结论：不接「今日校园」的只读数据；只做官方入口的外链/深链跳转（形态 A）；把已有的课表 SSO 抓取链路当作「存量技术债」冻结不扩展、校级化前替换掉。**（置信度：**高**，理由见 §2/§3/§4/§6）

| 项 | 判定 | 置信度 |
|---|---|---|
| **推荐方案** | **E + A 组合**：E＝不接入今日校园数据（复用官方 App/办事大厅/完美校园既有的东西，班级站只做官方没做的班级协作）；A＝在站内加「今日校园 / 网上办事大厅 / 完美校园」官方入口卡片（纯外链，零数据、零凭据、零接口） | 高 |
| **不推荐** | **B（安卓 WebView 内嵌 SSO）**、**C（服务端代登录抓取）**——技术上今天就能做（`jwxt/jwxt.py` 已证明 FJTCM authserver 可纯 requests 登录），但**合规与账号风险不可接受，且对 70 人班级的边际价值最低** | 高 |
| **唯一长期正路** | **D（学校授权：今日校园开放平台/门户上架校内 H5/统一认证授权接口）**——但申请主体必须是**学校**，个人/学生团队不可申请；现实中=学校立项后的 6–12 个月路径 | 中高 |
| **分档 go/no-go** | G0 班级级（现在，0–2 周）：**GO**（仅 A）｜G1 学院试点（2–8 周）：**GO，但不新增任何今日校园接入**｜G2 校级（6–12 个月）：**仅 D，其余 NO-GO** | 高 |
| **最关键 3 个卡点** | ① 官方门户已覆盖学生端 9/10 项需求（**重复建设**）；② **本校校规明文禁止**：《福建中医药大学信息系统用户管理规定》第十六条「**不允许共享账号**」，代登录同时缺第二十六/二十七条要求的合同、许可与工具安全检查——**校规层面已被否定，不必等到 PIPL**；叠加 2026 年多校（含福建省内）公开声明把「诱导提供账号密码 + 自动化抓取」直接定性为**违规/非法**、同类高校账号条款「严禁转借共享、可封号 7/30 天/永久」；③ 代登录=处理全校身份凭据，触发**委托处理 + PIA + 学校书面授权 + 等保**，个人主体一项都不适格 | 高 |
| **若只记一件事** | 「技术上能做到」与「可以做」在这个功能上是反向的：**越能做的形态（B/C）风险越高，风险最低的形态（A/E）恰恰也最该做**——因为今日校园是学校强制场景（报修/审批/出入证/奖助），学生本来就必须装它，**省掉一个 App 的收益≈0** | 高 |

**差异化定位提醒**：本班工具站真正被需要的是官方门户**没有**的东西——班级作业/通知板、抽签与分组、点名、体测录入、投票（含可见范围）、PPT 兼容包与多端下载、电费趋势与低电提醒、大屏。这些没有一项需要今日校园的数据（§6.3 价值排序）。

**关键校正：今日校园 ≠ 成绩/课表（跨校经验不可迁移）**

`01` 报告的核心事实指出：**HFUT 的「今日校园」= 学工系统 H5 容器，本身不含成绩/课表**——那些数据在教务系统（EAMS5）走另一条 API 链路；反之，FJTCM 的今日校园按校方指南**确实能看到成绩与课表**。两者不矛盾，原因是：

1. 今日校园/金智门户是**聚合容器**：把学校已建的各业务系统以「应用」形式挂进来（HFUT 是 50 个 `xsfw/sys/*` 应用；FJTCM 是办事大厅 86 个应用 + 今日校园公共服务）。**点进「成绩」「课表」「购电」应用，背后仍是各系统自己的登录态与页面**，不是今日校园的一个统一数据接口。
2. 因此「接今日校园」在工程上等于「接 **N 个系统**」：成绩→教务、课表→教务、一卡通→完美校园/一卡通平台、报修→后勤、奖助→学工，每一家都有自己的登录/协议/风控。
3. 这直接推翻「只要打通今日校园一次，就什么都有了」的直觉——**打通成本不是 1 次，是 N 次；每一次都要面对 §4/§5 的同一套风险**。
4. 也解释了为什么 HFUT-Schedule 对今日校园段只做「应用列表 + WebView」：它**不必**、也**没有**把每个应用的数据 API 化。

（置信度：高；`01` 报告与 `docs_HfutApi.md:1720` 相互印证，FJTCM 侧来自校方指南 2024-07-08）

**1.2 的结论**：即使 HFUT-Schedule 用 WebView + CAS 把今日校园页面「包」进自己的 App 并运行多年，**它也不能作为本项目「可以照做」的授权依据**——① 它是单体客户端，不收集/不转存他人数据；② 它仍可能违反所在学校的账号条款（公开渠道未见其获得 HFUT 授权）；③ 它不承担 70 人班级数据的合规责任。

### 1.4 本节结论

- 今日校园在本校是**全功能官方门户**（学生端 9/10 项能力已覆盖），且是**强制场景**（报修/奖助/审批/出入证/一卡通都在里面）→ 学生**不可能**因为它被替代而不装它。
- 因此「把今日校园功能搬进班级站」的目标收益≈「少点一次图标」，而成本是凭据、合规、封号、维护四类风险。
- **唯一值得吸收的不是它的数据，而是它的两个公开信息面**：校历/教学周（对齐作业 DDL 与课表周次）、公开公告（校级通知的权威口径）。这两项可以**手工维护或由公开页面转述**，不触发任何接口接入（见 §2 建议列）。

2. **2 项可强化入口**：官方入口外链（#全部）与公开公告转述（#10）。

### 3.3 推荐组合与不推荐理由

**推荐组合：E + A（现在）→ D/F（仅在校级授权成立后）**

> 术语：**F = D 的子形态**（§3.1 D 行 ②）——把班级工具作为 H5 应用**上架到今日校园/办事大厅**，用户从官方入口点进来、走学校 SSO。它是「我们进官方」，与「官方数据进我们」方向相反。

- **E 为主**：不新增今日校园数据源；官方能力交回官方 App。
- **A 为辅**：站内只放「官方入口」，把它做成**导航**而非**集成**——文案明确「官方 App/官方门户，非本站功能」。
- **D/F 为长期目标**：唯一既合规又有体验收益的形态是「**我们的 H5 被上架进今日校园**」（学校管理员配置 + 学校 SSO），方向与「把今日校园搬进我们站」**正好相反**——即「我们进官方」而不是「官方数据进我们」。这条路径的前置是学校立项，个人不可启动（§7.3）。

**不推荐 B 的理由（看起来最轻，实则最夹生）**

1. **它仍要求用户向第三方 App 提供统一身份认证账密**——与「严禁向第三方提供账号密码」的校方口径直接冲突（§4.2 Q1）；「不落库」只能降低泄露面，**不能改变「第三方收集了账密」这件事**。
2. **技术上是半成品**：HFUT 的做法是「原生 CAS 登录 → 把 cookie 注入 WebView」，WebView 本身不承担登录；若改成「用户在 WebView 里登录」，就要处理验证码、扫码、多因子、UA 白名单、cookie 域、跨域下载/上传、返回键、支付类拦截——**工作量接近自研一个壳**（3–5 人日只是起步），收益却只是「少切一次 App」。
3. **不可控的兼容性**：金智 H5 可能依赖容器桥（`bh-mobile-sdk` 的 `closeWebView` 等），裸 WebView 里可能出现「关闭按钮无效/上传失败/白屏」，且改版即坏。
4. **合规定性不会因为「只是 WebView」而变好**：这一形态的实质仍是「第三方 App 承载学校登录页」。

**不推荐 C 的理由（技术上最诱人，风险最高）**

1. **本校校规硬性禁止**：《福建中医药大学信息系统用户管理规定》**第十六条「每个用户必须被分配唯一的账号……不允许共享账号」**；第二十六/二十七条要求第三方访问信息系统须**合同＋保密协议＋部门许可＋权限限制＋工具安全检查**。代登录同时命中这两条（§4.1 行 9a/9b）。
2. **一个 CAS 登录换来的数据面极宽**：HFUT 的证据显示，CAS ticket 可换学工 API token，token 能读**成绩、考试、宿舍、图书馆借阅、校园地图、同学列表、应用列表**——**技术上无法「只要课表」**，直接违反最小必要。
3. **维护是永续对抗**：HFUT-Schedule 为维持登录专门**训练了验证码 OCR 模型**（Tesseract5，用「爬取 1000 张验证码图片」训练，`tools_Captcha-Ocr/README.md`）——这等于**以技术手段规避学校的安全控制**，在校方 2026 年声明语境下性质更严重；不做 OCR 就要人工输入验证码 → 无法自动化 → C 的价值归零。
4. **失败代价由同学承担**：封号 7/30 天/永久（§4.1 行 9c），且统一认证账号贯通教务、邮箱、一卡通、审批（§4.2 Q1）。
5. **存量链路已足够说明问题**：本工程课表链路只服务**运营者本人 1 个账号**，且允许人工兜底（`sync.py --manual`）；扩到 70 人＝把「1 个账号的灰度试验」变成「70 个账号的集中托管」，风险形态质变。

**A 的边界（防止「外链」被误用成「集成」）**

- 允许：跳转官方 App/门户/应用商店、复制官方链接、安卓 intent 拉起。
- 禁止：把官方页面套 iframe 伪装成站内功能（`X-Frame-Options`/CSP 通常也会拦）；禁止在跳转前后收集/回传任何参数；禁止用「本站可查成绩」之类文案引流。
- 现状核查点：小程序内无法跳外部 App，**不要在审核文案里暗示能查成绩**（会触发微信类目/内容审核风险）。

### 4.2 五个关键问题逐条判定

#### Q1「代登录」是否等同于「账号共享」？→ **是；本校校规已明文禁止，仅有用户同意不能消除定性**（置信度：高）

- **本校已有直接条款**：《福建中医药大学信息系统用户管理规定》第十六条「**不允许共享账号**」。用户把统一身份认证账号密码交给本系统（或本系统的本机 agent）代其登录，语义上就是「账号由非本人使用/交第三方使用」，且第三方访问还须满足第二十六/二十七条的合同、许可、工具检查——**本项目一条都不满足**。
- 用户把自己在 `authserver.fjtcm.edu.cn` 的账号密码交给本系统（或本系统的本机 agent），由系统代表用户登录 → 在账号条款语义上同时构成「转借/共享」与「**代为操作**」（山西工程原文即「严禁将账号密码告知他人代为操作」）。
- **用户的民事同意 ≠ 对学校账号规则的豁免**：账号是学校基于身份发放的，使用条件由学校设定；用户无权把自己的账号「授权」给第三方以规避学校规则（这与「数据主体同意即可处理」不是同一层问题：一个是个人信息处理的合法性基础，一个是**信息系统访问权限的授权链**）。
- 即使凭据只存在用户本机（B 形态）或只存在本机 DPAPI 加密文件（C 形态的现状课表链路），**系统仍是「第三方软件」**——2026-07 厦门大学嘉庚学院（**福建省内**）的安全警示把「非官方小程序/第三方 APP 以绑定教务账号查课表、成绩」列为风险并要求「**禁止向任何第三方小程序、软件、网站提供教务系统账号密码**；曾使用第三方平台绑定账号的同学请立即修改密码、解除授权」— [通知原文](https://it.xujc.com/2026/0717/c6729a172095/page.htm)（2026-07-17）。
- 置信度说明：**FJTCM 本人条款未见公开版**；但①本校 2022 申报通知要求校内系统统一身份认证登录（暗示认证由学校统一管理）；②福建同省高校 2026 年已明文禁止；③2026 年多校（长沙理工、厦大嘉庚）密集发声明，说明这是当前治理重点。故判「高」，但「本校是否会对学生个人封号」标**中**。

#### Q2 是否构成「越权访问」？→ **只读本人数据=违约+合规瑕疵；批量/他人数据=可能触及刑事红线**（置信度：中高）

| 场景 | 定性 | 风险等级 |
|---|---|---|
| 只读**本人**数据、凭据仅存本机、仅本人可见 | 主要违反学校账号条款/系统使用规定（**违约**）；个人信息处理上有用户同意的基础，但「访问授权链」仍不完整 | 中高 |
| 只读本人数据但**上传云端**/跨端同步/给班级看 | 叠加「未经学校授权处理学校数据+二次分发」；若含他人信息则更重 | 高 |
| 代**他人**登录 / 批量拉取全班 | 可能构成《网络安全法》27 条禁止行为；情节严重可能触及《刑法》285 条第 2 款（非法获取计算机信息系统数据） | 极高（红线） |
| 破坏/篡改/提交表单（选课、评教、报修代填） | 明确越权操作 | 极高（禁止） |

**学校立场已经非常明确**（这决定「技术上能跑通」不等于「默许」）：

- **长沙理工大学**（2026-03-27）：「从未授权任何校外第三方应用程序、商业机构接入或访问我校教务管理系统……任何未经我校明确授权，通过任何技术手段（**包括但不限于诱导学生分享账号密码、自动化脚本抓取、系统漏洞侵入**等方式）非法获取、使用我校教务管理系统内数据的行为，均涉嫌违反《网络安全法》《数据安全法》《个人信息保护法》」— [严正声明](https://www.csust.edu.cn/jwc/info/1101/7727.htm)
- **厦门大学嘉庚学院**（2026-07-17，福建省内）：第三方会「完整保存登录凭证」，可获取学籍/成绩/综测/奖惩，且教务账号**连通校内邮箱、教学文件系统、图书馆、教室预约、报修平台**，「第三方获取权限后，可篡改选课、删除作业、查看邮件、取消场地预约」— [安全警示](https://it.xujc.com/2026/0717/c6729a172095/page.htm)
- **长江大学**（2020-01-03）：第三方「助手」类软件「使用第三方爬虫软件非法爬取教务系统相关数据」，学校呼吁抵制并加强监管 — [声明](https://jwc.yangtzeu.edu.cn/info/1083/6416.htm)
- **历史事故链**：2015 年**福建**厦门某高校因学生把教务账密交给微信公众号代查，第三方反复登录抓取导致教务系统不可访问，学校随后**加验证码 + 限制校内网访问** — [海西晨报/厦门网](http://xm.fjsen.com/2015-01/25/content_15598233.htm)（2015-01-25）。**这个案例同时说明：这类接入的终局是学校加固，接入方全部失效。**

#### Q3 是否需要学校书面授权？→ **只要「组织使用 + 取学校数据 + 用统一身份认证」三者任一成立，就必须**（置信度：高）

- 校级/学院级推广 → 教APP备使用者备案主体是学校（02 §2.5）；统一身份认证对接 → 需学校注册/授权（01 §3.3「依赖学校授权，周期与结果不可控」）；使用学校名称/校徽/「官方」字样 → 需书面授权（02 §2.8）。
- 即使用户「纯自发、班级内、不具名」，**取数行为本身**仍缺学校授权 → 属「学校是否追究」而非「是否合规」的问题。
- 结论：**任何 B/C/D 形态在学院级及以上都必须有学校书面授权**；班级级没有授权就没有合法性基础，只能靠「学校不追究」的默许——而 2026 年的治理环境（§4.2 Q2 多校声明 + 02 报告的 95.68% 备案率）说明默许窗口正在关闭。

#### Q4 数据最小化与保存期限 → **代登录形态天然违反最小必要**（置信度：中高）

- 代登录一次登录即获得该账号在目标系统的**全部可见数据**（学籍、成绩、奖惩、邮箱、一卡通、报修记录……），无法做到「只要课表」；最小必要原则要求按功能裁剪，而这在页面抓取形态下**技术上不可裁剪**（你拿到的是整个 session）。
- 保存期限：02 §3.5 的建议基线（课表 1 学年、成绩按需、日志 6 个月、账号在校+毕业后 6–12 个月）在代登录形态下需要额外定义「凭据」与「cookie/ticket」的保存期限——**凭据本身不属于可为业务目的长期保存的个人信息**，只能「用完即弃 + 用户可撤销」。
- 现状差距：本站 `userdata`/`marks` 等仅覆盖不物理删、保留期未定义（02 §3.5 末尾，存量审计 H-3/H-9）→ **在补齐删除/保留期机制之前，不应再新增一类高敏数据（成绩/学籍）**。

#### Q5 是否触发 PIA（个人信息保护影响评估）？→ **触发，且应由学校牵头**（置信度：高）

按 PIPL 第 55 条逐项比对：

| 触发情形 | 本项目是否触发 | 说明 |
|---|---|---|
| 处理**敏感**个人信息 | ⚠️ 视功能而定 | 体测/团员身份/水电时序（02 保守按敏感）；若接入成绩/学籍，虽非敏感但属高保护数据 |
| **委托处理** | ✅ 触发 | 学生团队/云厂商受托；代登录链路中「用户→学生系统」也是典型的「他人代为处理」 |
| 向他人**提供/公开** | ✅ 触发 | 数据进 CloudBase/对外 API；OSS 香港公共读（02 §3.6） |
| **向境外提供** | ✅ 触发（现状） | OSS 香港存含个人信息的媒体/附件（02 §3.6） |
| 自动化决策 | ⚠️ 可能触发 | 若做「成绩预警/挂科预测/排名」即属自动化决策，需 PIA + 透明度 + 拒绝权 |

→ **PIA 是硬性的**；且 PIA 责任主体应为学校（处理者），学生团队是受托方。**在 PIA 未做之前新增代登录数据源，等于在未评估的高风险处理上叠加新处理活动。**

### 4.4 硬性阻断（red flags，命中任一即不可行）

1. 把统一身份认证**账号密码**提交给本项目（本机或云端）→ 违反本校《信息系统用户管理规定》**第十六条「不允许共享账号」** + 缺第二十六/二十七条的合同/许可/工具检查（Q1/Q3）。
2. 代**他人**登录或批量拉取全班数据 → 跨越「越权/非法获取」红线（Q2）。
3. 未经学校书面授权使用学校名称/校徽/「官方」字样做入口说明（02 §2.8）。
4. 在未完成 PIA、委托协议、删除/保留期机制前新增成绩/学籍类数据（Q4/Q5）。
5. 由学院/辅导员/班委**组织**使用却未做教APP备使用者备案（02 §2.5）。
6. 将含个人信息的今日校园数据落到**香港 OSS 公共读**（出境+公开，02 §3.6）。

| **验证码（最大单点）** | `AUTH_CAPTCHA_URL = .../authserver/checkNeedCaptcha.htl`；`check_need_captcha()` 命中即 `raise LoginError("统一认证要求输入验证码，无法自动登录")`（`jwxt.py:69`/`:552`/`:620`）。对照：HFUT-Schedule 的 CAS **必带 4 位图片验证码**（`docs_HfutApi.md:71–81`），项目为此**自训 Tesseract5 OCR 模型**（爬 1000 张验证码训练，`tools_Captcha-Ocr/README.md`） | 一旦学校开验证码，**全部自动化链路当场失效**；想维持就要做 OCR＝**规避安全控制**（性质升级）；否则退回人工（`sync.py --manual`），C 形态价值归零 | 高 |

| 1 | 通知板 + 作业 | 班级日常高频、官方不覆盖班级粒度 | 无需接入 |

**6.3 结论**：接入今日校园数据在价值排序里排 **8–9 名**（末位），而它的风险排 **第 1 名**。这是本议题最核心的取舍依据。

### 6.4 风险成本（不可忽视的「负收益」）

- **封号成本**：一名同学账号被封 7–30 天 → 教务选课/成绩、邮箱、一卡通、审批、出入证受影响；若因本工具导致，**班级信任一次性归零**（且不可逆）。
- **组织成本**：一次约谈/通报会直接冻结整站（对比 2026-01 某双非高校案例：教务中间件被要求全部下线、学院约谈、书面说明数据来源）。
- **时间成本**：任何一次学校侧加固（验证码/限校内网）都会产生「紧急下线 + 解释 + 回滚」的 3–10 人日隐性成本，且没有预算来源。

| M5 | **CloudBase 2026-12-10 到期**（距今 27 天）：续费/迁移优先于任何新功能 | 避免「功能还在、后端没了」 | 见 `school_scale_20261113/03`（容量与成本） |

**长期（仅当 D/F 成立）**：学校立项 → 等保定级备案 → 统一认证对接或 H5 上架 → 数据境内 → 学校主体运维；周期 6–12 个月，个人无法启动（02 §9、04 §5.5 G3）。

### 7.3 前置条件（若要进入 B/C/D 任一形态，缺一不可）

1. **学校书面授权**：明确接入范围（哪些系统、哪些字段、只读）、名义（不得用校名校徽）、责任划分。
2. **安全评估**：等保定级备案（二级）+ 上线前第三方检测/代码审计；代登录模块须单独做接口风险评估。
3. **凭据方案**（仅 B/C 相关）：用户明确授权 + 终端加密 + 不落服务端明文 + 一键撤销 + 失败即停；**且须学校书面同意「允许代操作」**——按 §4.2 Q1 判断，这一条现实中几乎不可能拿到。
4. **数据最小化与期限**：字段白名单、仅本人可见、保留期定义、删除入口（现状差距见 02 §3.5）。
5. **监控与回滚**：可用性探测 + 改版告警 + **kill switch**（一个开关关闭全部外部数据接入并清缓存）；任一异常先停后查。
6. **运维主体**：≥2 人 + 1 位老师 + 交接文档（单人/毕业即断供，01/03 报告一致结论）。

### 7.4 不推荐的理由（汇总，5 条）

1. **收益≈0**：今日校园是学校**强制**门户（报修/审批/出入证/奖助/一卡通都在里面），学生本来就必须装；班内「少点一次图标」的边际价值极低，§2 矩阵 16 项里只有 1 项（校历）值得自建。
2. **本校校规直接禁止**：《信息系统用户管理规定》第十六条「不允许共享账号」+ 第二十六/二十七条第三方访问须合同授权 → 代登录在**校规层面**即可被否定，不需要等到 PIPL 层面（§4.1 行 9a/9b）。
3. **学校立场已明确**：2026 年多校（含福建省内厦大嘉庚 2026-07）公开把「诱导提供账号密码 + 自动化抓取」定性为违规/非法，并保留追责（§4.2 Q2）。
4. **维护不可持续**：HFUT-Schedule 用「自训验证码 OCR + 应用列表 token + WebView」维持，且对学工 API 明确放弃（"登录参数比较多，需要 JS 逆向"）——**同类项目的最佳实践也只是「外链 + WebView」**，而不是我们自研代登录。
5. **机会成本最高**：13–20.5 人日 + 永续维护，本可投入到 CloudBase 搬迁（27 天到期）、隐私/删除机制、PPT/投票既有缺陷——这些才真正影响 70 人日常。

### 7.5 一句话给用户

> 想「少装一个 App / 少点一次」的诉求不值得用「同学账号可能被封、学校可能约谈、代码要我一个人永远维护」去换；把今日校园当**官方入口**供起来（A），把力气花在官方**没有**的班级协作上（E）——如果哪天真要打通，唯一正确的姿势是**让我们的东西进官方门户**（D/F），那件事必须由学校牵头，而不是我们去绕。

### 7.6 需要写进 AGENTS.md 的建议红线（供 Lead 决策，非本任务范围）

1. 不得代任何用户（含本人以外）登录学校系统；不得在服务端/云端保存统一身份认证凭据。
2. 不得采集「今日校园/学工/教务」数据用于班级站展示；课表为**存量例外**，且不得扩展。
3. 任何「官方入口」只做跳转，不得 iframe 包装、不得改文案暗示本站可查官方数据。
