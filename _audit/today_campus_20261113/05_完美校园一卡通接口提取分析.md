# 05 · 完美校园一卡通接口提取分析（仿 HFUT-Schedule 的方法）

> **2026-11-14 补充（用户实测）**：完美校园开放平台 `open.17wanxiao.com` 的**注册功能已停止使用**（个人开发者注册入口不可用）→ **路线 A（官方 OpenAPI）正式关闭**。后续按本文路线 B（App 协议复刻，只读）或 C（快捷入口/手动记账）推进；B 需要用户本人抓一次 `YKT_Interface/xyk` 余额/流水请求来补齐 method/param。

> **目标**：回答「HFUT-Schedule 的今日校园/一卡通是怎么做的」，并把同样的方法套到 **FJTCM 的完美校园（新开普）** 上，给出**可落地的接口提取结果与实现路线**。
> **日期**：2026-11-14｜**范围**：只读分析 + Android 侧方案；不包含充值/支付/挂失等写操作。
> **来源**：HFUT-Schedule 公开源码（本地缓存 `_scratch_repo/`，899 文件）、完美校园官方开放平台公开页面、公开的完美校园逆向工程代码（GitHub，MIT）、校方公开文档。**未登录任何真实账号、未使用真实凭据、未向完美校园发起任何请求**。
> **置信度**：高＝代码/官方页面直接证据；中＝公开逆向代码/文档片段（可能过时）；低＝推断。

## 1. HFUT-Schedule 到底怎么"提取"的

### 1.1 它其实做了两套完全不同的东西

| 层 | 对象 | 做法 | 证据 |
|---|---|---|---|
| **A. 今日校园（学工系统 H5）** | `stu.hfut.edu.cn/xsfw/sys/...` | **不逆向业务接口**：CAS 统一认证拿票据 → 换学工 `_WEU` cookie → WebView 注入 cookie 打开 H5；应用目录用内置快照 + 智慧社区动态补充 | `01_今日校园接口分析_HFUT-Schedule.md` §2/§3/§4 |
| **B. 一卡通/电费/网费（慧新易校）** | `121.251.19.62`（慧新易校） | **真·接口提取**：本人登录拿 `synjones-auth` token → 直接调厂商 REST API（余额/流水/统计/缴费）→ 本机展示 | 本文件 §2；`HuiXinService.kt`、`HuiXinRepository.kt`、`docs/HfutApi.md` L964–1044 |

**关键**：HFUT-Schedule 对「今日校园」只做壳，对「一卡通」才是接口级提取。用户想要的「仿照他把完美校园接口提取出来」，对应的是 **B 层（厂商 API）**，不是今日校园 H5。

### 1.2 B 层的完整链路（慧新易校，HFUT 版）

1. **登录（两条路）**
   - CAS OAuth（优先）：教务 CAS cookies → `GET https://cas.hfut.edu.cn/cas/oauth2.0/authorize?client_id=Hfut2023Ydfwpt&redirect_uri=...` → 302 `Location` 带 `synjones-auth=<token>` → `GotoInterceptor` 截获存本机。
   - 密码直登（兜底）：`POST /berserker-auth/oauth/token`，form `username=学号&password=一卡通密码(默认身份证后6位)&grant_type=password&logintype=sno`，Header `Authorization: Basic base64("mobile_service_platform:mobile_service_platform_secret")` → `access_token`。
2. **调用**：所有接口 Header `synjones-auth: <token>`；余额 `GET /berserker-app/ykt/tsm/getCampusCards`、流水 `GET /berserker-search/search/personal/turnover?current=&size=`、月统计 `GET /berserker-search/statistics/turnover/sum/user?...&dateStr=YYYY-MM`、区间总额 `GET /berserker-search/statistics/turnover/count?timeFrom=&timeTo=` 等。
3. **失效检测**：任一接口 body 含「操作成功」= 有效；失效后重新走登录。
4. **落点**：token/密码只存本机（SharedPrefs/DataStore）；金额「分→元」；展示 + 本地统计/预测；付款码/挂失/改密不自己实现，WebView 打开官方 H5 并带 token。
5. **前提**：**个人客户端**（只服务本人、无服务端、无多人数据）；这也是它敢这么做的原因。

### 1.3 可复用的"提取方法论"

> ① 找目标系统的**登录入口**（统一认证或业务系统自己的登录）→ ② 拿到 **token/cookie** → ③ 用 App/网页同款 **REST 接口**取数（不逆向加密协议本身，除非必须）→ ④ **本机缓存/展示** → ⑤ 失效就重登、失败就降级 → ⑥ 写操作（支付/挂失）尽量交给官方 H5/App。

## 2. 完美校园接口面（FJTCM 一卡通平台）

### 2.0 先对齐事实

- FJTCM 校园卡充值/查询官方渠道是 **完美校园（新开普）**：校后勤处《关于校园卡充值业务办理须知》明确「圈存机或完美校园 APP 充值」；今日校园里的「一卡通」入口实际会**跳转完美校园 App**（多校使用说明一致：今日校园 → 一卡通 → 跳完美校园）。
- 因此我们要提取的是 **完美校园** 的接口，不是今日校园的。
- 完美校园有两类接口：
  - **App 私有协议**（登录加密 + `YKT_Interface` RPC）；
  - **官方开放平台 OpenAPI**（OAuth2 + `api/1/ecard/*`，需注册/审核）。

### 2.1 App 私有协议（公开逆向代码已确认的部分）

> 来源：GitHub 公开项目 `w1278640538/17wanxiaoCheckin`（MIT，2021-2022）中的 `login/campus.py`、`api/ykt_score.py`、`api/user_info.py`；原逆向作者 zhongbr/ReaJason。**2021 年后完美校园换过登录接口，以下为当时版本，当前是否可用需实测**（置信度：中）。

**A. 密钥交换**

```
POST https://app.17wanxiao.com/campus/cam_iface46/exchangeSecretkey.action
Header: User-Agent: Dalvik/...（完美校园 App UA）
Body(JSON): {"key": "<客户端生成的 RSA-1024 公钥>"}
响应: RSA 私钥解密的 JSON → {"session": "<sessionId>", "key": "<24字节 appKey>"}
```

- `appKey = key[:24]`；`sessionId` 之后就是 **token**（脚本里 `token = sessionId`）。
- 响应本身是 RSA 加密的，客户端要自己生成 1024 位 RSA 密钥对。

**B. 密码登录**

```
POST https://app.17wanxiao.com/campus/cam_iface46/loginnew.action
Header: campusSign: sha256( json(upload_args) )
Body(JSON):
  {
    "session": "<sessionId>",
    "data": DES3( JSON(login_args), key=appKey, IV="66666666" )   // Base64
  }
login_args:
  appCode=M002, deviceId=<设备ID>, netWork=wifi, qudao=guanwang,
  requestMethod=cam_iface46/loginnew.action, shebeixinghao=<手机代号>,
  systemType=android, telephoneInfo=<系统版本>, telephoneModel=<机型>,
  type=1, userName=<手机号>, wanxiaoVersion=<app 版本号>, yunyingshang=07,
  password=[DES3(每个字符, key=appKey, IV=66666666), ...]
```

- 失败码：`该手机号未注册`、`您正在新设备上使用完美校园，请使用验证码进行验证登录`、`密码错误...`（`login_campus.py` L120–129）。
- **设备校验**：同一账号只允许一个 `deviceId`；第三方客户端要么复用官方 App 的 device_id（需 hook/抓包），要么会被要求短信验证/顶掉手机端登录。**这是复刻路线最大的坑。**

**C. 短信登录**

```
POST .../cam_iface46/gainMatrixCaptcha.action   → 发送短信（action=registAndLogin, deviceId, mobile, type=sms）
POST .../cam_iface46/registerUsersByTelAndLoginNew.action → 验证码登录，返回 token
```

**D. 一卡通 RPC（核心）**

```
POST https://server.17wanxiao.com/YKT_Interface/xyk    （亦见 server.59wanmei.com）
Header: Content-Type: application/x-www-form-urlencoded
Body: token=<token>&method=<METHOD>&param=<URL编码的JSON>
```

- 已确认 method：**`WX_BASE_INFO`**（打开完美校园「校园卡」时抓到的第一个请求）→ 返回 `data.customerName`（学校名）等（`api/user_info.py::get_school_name`）。README 明确指路：`完美校园 App → 全部应用 → 打开校园卡时抓包【server.17wanxiao.com/YKT_Interface/xyk】【请求体中 method=WX_BASE_INFO】`。
- **余额/交易明细的 method 名在公开代码里没有出现**（置信度：低，需实测）。按同族命名推断候选：`WX_CARD_INFO` / `WX_CARD_BASE`（卡信息+余额）、`WX_TRADE_LIST` / `WX_TRADE_DETAIL`（交易明细）、`WX_CARD_LOSS`（挂失）等；**method/param 必须用你自己的账号抓一次 App 请求确认**。
- 同接口族还有 `POST https://server.17wanxiao.com/YKT_Interface/score`（粮票/签到，form 同上）——说明这是**一个 servlet 按 method 分发的 RPC 网关**，不是 REST 资源风格。

**E. 其他已知域名（旁证）**

| 域名 | 用途 | 证据 |
|---|---|---|
| `app.17wanxiao.com` | App 登录/密钥交换（`cam_iface46/*`） | 逆向代码 |

### 2.2 官方开放平台 OpenAPI（更规范的第二条路）

官方页面 `https://open.17wanxiao.com`（完美校园开放平台，新开普）：

- **个人开发者（学生/老师）可注册**；公共免费接口注册/填写应用信息后可用；非公共接口需应用审核后在「高级页面」申请；「商谈」接口需联系平台。
- **一卡通接口清单**（官方「个人开发者」页面原文，置信度：高）：
  - `api/1/ecard/base` 一卡通基本信息（normal，免费）
  - `api/1/ecard/surplus` **余额**（high，需申请）
  - `api/1/ecard/trade/detail` **交易明细**（high，需申请）
  - `api/1/ecard/fund` 领款项记录（high）
  - `api/1/ecard/pwd/update` 修改查询密码（high）
  - `api/1/ecard/lose` 挂失（high）
  - `api/1/ecard/unbind` 解绑（high）
  - `api/1/ecard/pick` 捡卡登记（normal）
  - `api/1/ecard/get/bank` 银行签约列表（high）
  - `api/1/captcha` 验证码（normal）
- 用户信息：`api/1/user/base`（normal）、`api/1/user/base_senior`（high）、`api/1/user/info/super`（super）等；支付：`api/1/wxpay/gateways`、`api/1/user/order`、`api/1/wxpay/query`。
- **授权**：Authorization Code（`https://api.17wanxiao.com/api/authorize` 打开完美校园登录授权页 → `code` → 换 `access_token`），access_token **3600s**、refresh_token **14 天**；另有 Refresh Token 刷新；测试域名 `api.17wanxiao.com`，正式域名 `open.17wanxiao.com`（文档原文）。
- **风险**：平台页面/公告停留在 2017（页脚 ©1998–2017，系统公告最后 2017/4/28），部分文档页已 404；**是否还受理注册/审核、high 权限能否批给个人，需要你实际试一次**（置信度：中低）。

### 2.3 不可行的路径（先排除）

- **网页/H5 直达**：今日校园网页版无工具（用户已实测），完美校园也没有面向学生的「一卡通」网页版；不存在可内嵌的 URL。
- **微信/支付宝小程序**：完美校园有支付宝小程序/微信卡包，但第三方 App 不能嵌入小程序页面取数，只能跳转（无法满足「工具内看余额/流水」）。
- **WebView 套壳官方 App 页面**：完美校园 App 是原生 + 私有协议，没有可用的 H5 页面承载一卡通。

## 3. 两条提取路线对比

| 维度 | 路线 A：官方开放平台 | 路线 B：App 协议复刻（HFUT 同款） |
|---|---|---|
| 登录 | OAuth2 授权码（完美校园账号登录授权） | 交换密钥 → DES3 加密登录（账号密码/短信），device_id 设备校验 |
| 一卡通取数 | `api/1/ecard/surplus` / `trade/detail`（需 high 权限） | `YKT_Interface/xyk` + method（余额/流水 method 名待抓包确认） |
| 合规性 | **官方渠道**，按平台协议；需注册/审核 | 第三方 App 协议，**可能违反用户协议**；单设备限制会与官方 App 冲突 |
| 稳定性 | 有文档/版本；但平台可能停更 | 无文档/SLA，App 改版即失效；加密/签名/字段易变 |
| 前置条件 | 注册个人开发者 → 创建应用 → 审核 → 申请 high 接口 → 拿 client_id（client_secret 放本机，不入库） | 需要你本人账号 + 一次抓包确认 YKT method/参数；或复用 device_id（需 hook） |
| 建议 | **首选** | 仅在 A 不可用时、且你接受风险，做**只读** PoC；绝不做支付/挂失写操作 |

**明确建议**：先花 10 分钟去 `open.17wanxiao.com` 试注册（个人开发者/学生 → 应用管理 → 新建应用），看：
1. 注册/登录是否还正常；
2. 能不能创建应用、要不要审核；
3. 有没有「高级接口申请」入口、能不能申请 `ecard/surplus`、`ecard/trade/detail`；
4. FJTCM（schoolcode 769）是否在平台覆盖。

若 A 通：我按官方 OAuth 做 App 内一卡通工具（只读）。若 A 不通：退回 C（快捷入口/手动记账），或你同意后做 B 的只读 PoC（你提供自己抓的请求样本，敏感字段脱敏）。

## 4. 在我们 Android App 的落地设计（以 A 为主，B 备选）

### 4.1 功能范围（只读）

- 余额（含未结算/可余额提醒）；
- 交易明细（分页/搜索/日期范围）；
- 本月/近 30 天消费统计（本地算）；
- 低余额提醒（本地阈值，可选通知）；
- **不做**：充值、支付、付款码、挂失/解挂、修改密码（这些继续走官方完美校园 App）。

### 4.2 模块划分（与现有工程风格一致）

```
data/card/
  CardApi.kt          // OpenAPI 接口定义（Retrofit/OkHttp）；或 B 路线 YKT RPC
  CardRepository.kt   // 拉取/解析/缓存/失败降级
  CardTokenStore.kt   // OAuth token/refresh 仅本机（Keystore/EncryptedSharedPreferences）
features/card/
  CardModels.kt       // 余额、交易记录、统计
  CardLogic.kt        // 分→元、日期窗口、统计、低余额判断（纯 JVM 可测）
ui/screens/card/
  CardScreen.kt       // 余额 hero + 明细列表 + 筛选
```

- 工具卡：`ToolCatalog` 新增 `id="card"`、名称「一卡通」、分类 `CLASS`、可拖入首页快捷；
- 路由：`MainNavHost` 加 `"card" -> CardScreen(...)`；
- 使用说明加 1 张卡（21→22，`VERSION` 顺延）；
- 版本：待 Android 并行会话收口后顺延（建议 v4.48.0/vc66）。

### 4.3 凭据与安全（红线）

- OAuth 的 `access_token/refresh_token` 只存**本机** Keystore/EncryptedSharedPreferences，不上传/不同步/不日志；
- `client_secret` **不入库**：放 `local.properties` 或本机配置文件（`.gitignore`），构建时注入；
- 每用户各自授权，**不服务端代管、不代他人查询**；
- 明细不导出、不分享、不展示学号/卡号（只显示卡号后 4 位或掩码）；
- 只读；任何写操作（充值/挂失）不做，引导官方 App；
- 抓包/逆向路线（B）若要实施：**只用你本人账号**，样本脱敏，不共享 device_id/密码；先确认平台条款风险。

### 4.4 测试

- 纯 JVM：加密/登录参数构造（若 B）、JSON 解析、分→元、日期统计、低余额阈值、token 失效重试逻辑（mock 网络）；
- UI mock：余额/明细/空态/错误态/加载/下拉刷新/无溢出；
- 真实数据：由用户在 APK 上用自己的账号授权/登录验证（自动化测试不得使用真实账号，遵循仓库既有红线）。

## 5. 风险清单

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| R1 | 官方平台已停更/不受理个人开发者 | 路线 A 不可行 | 先实测注册；不行转 C |
| R2 | high 权限（余额/明细）不给个人 | 拿不到数据 | 申请说明用途（班级内部、只读、非商用）；不行转 B/C |
| R3 | App 协议反编译/复刻违反用户协议 | 账号/法律风险 | 仅作最后手段；只读；本人账号；不传播 |
| R4 | 单设备校验（device_id）顶掉官方 App 登录 | 用户体验崩坏 | B 路线必须评估；A 路线无此问题 |
| R5 | 加密/签名/接口改版 | 功能随时失效 | 只读 + 失败降级 + 官方 App 兜底入口 |
| R6 | 财务数据敏感（余额/流水） | 隐私/合规 | 仅本人可见、不导出、不分享、不展示完整卡号 |
| R7 | 平台审核周期/资质要求 | 项目延期 | 先做入口卡/手动记账占位 |

## 6. 结论

1. **HFUT-Schedule 的做法可拆成**：「今日校园 = H5 壳（CAS + cookie + WebView）」+「一卡通 = 厂商 API 直连（token + REST + 本机缓存）」；后者才是接口提取，且建立在**个人客户端**前提上。
2. **完美校园的接口面已提取到**：
   - App 登录协议（RSA 交换密钥 → DES3 加密请求 → `campusSign` → token=session）——已从公开逆向代码确认（2021 版，需实测）；
   - 一卡通 RPC 入口 `POST server.17wanxiao.com/YKT_Interface/xyk`（token/method/param），已确认 `WX_BASE_INFO`；**余额/流水 method 名需抓包确认**；
   - 官方 OpenAPI 一卡通接口清单（`api/1/ecard/base|surplus|trade/detail|...`，OAuth2，high 权限需申请）。
3. **推荐路线 A（官方开放平台）**，只做只读余额/明细/统计；A 不通再考虑 C（快捷入口/手动记账）；B（App 协议复刻）仅在用户明确接受风险且提供本人抓包样本时做只读 PoC，**不碰支付/挂失**。
4. **当前卡点**：需要你实测完美校园开放平台注册/审核；Android 仓库并行未提交改动收口后才能落代码。

## 7. 校园码 / 充值能否集成（2026-11-14 用户追加问题）

### 7.1 结论

| 功能 | 能否集成 | 原因 | 可做的替代 |
|---|---|---|---|
| **校园码（虚拟卡付款码）** | **不能**（不建议做任何尝试） | 它是**动态支付凭证**：由完美校园 App/支付宝/微信小程序在官方体系内生成，绑定账号+设备+消费密码；第三方复刻=伪造/代理支付凭证，属于资金安全红线，且完美校园单设备/风控会拦截 | 工具卡内做「打开付款码」＝跳转**完美校园 App**（或支付宝/微信「完美校园」小程序），不生成、不显示、不保存任何码 |
| **充值** | **不能** | 涉及微信/支付宝/银行卡支付渠道、商户资质、资金结算与对账，主体是学校+新开普；个人/学生 App 不能成为支付服务提供者；完美校园开放平台**注册已停**，`api/1/wxpay/*` 等支付接口也不对个人开放 | 工具卡内做「去充值」＝跳转完美校园 App / 支付宝·微信完美校园小程序官方充值页，资金不经过我们的 App |
| **挂失/解挂/改密** | 不建议自己调接口 | 写操作，影响实体卡资金/使用；官方仍有入口 | 跳转完美校园 App / 官方 H5（`campus-card/cardOperation` 类页面，若完美校园有等价 H5） |

### 7.2 为什么 HFUT-Schedule 看起来"能"

- HFUT 的「付款码」不是它自己生成的：`HuiXinPayQuickButton` 用 **WebView 打开慧新易校官方 H5** `plat/pay?synjones-auth=<token>`（token 是官方登录换来的），码由**官方页面**生成；
- HFUT 的「缴费」是调慧新易校官方接口用**校园卡余额**给网费/电费/洗浴下单（`charge/feeitem/getThirdData` + `blade-pay/pay` 三步），属于写操作/支付，风险由用户自担；它**没有**做银行卡/微信充值；
- 完美校园没有等价的公开 H5 付款码页可套，且 App 协议有设备绑定——所以「复刻校园码/充值」比 HFUT 更不可行。

### 7.3 推荐的安全形态（如果只是要方便）

「一卡通」工具卡内提供（**只读 + 跳转**）：

1. 余额 / 交易明细（接口打通后展示；否则显示上次缓存 + 「打开官方 App」）；
2. **打开付款码** → 拉起完美校园 App（需真机确认 package/scheme；否则打开 App 首页）；
3. **去充值** → 拉起完美校园 App / 支付宝·微信「完美校园」小程序（跳转，不收款）；
4. **挂失/改密** → 跳官方入口。

红线：不生成/不缓存动态码；不接入支付回调；不保存支付密码/银行卡；不代替用户在官方页面完成支付。

### 7.4 为什么不能"直接把官方 App 集成进来"（2026-11-14 用户追问）

**结论：Android 上没有"把另一个 App 嵌进自己 App"的通用能力；只能跳转，或嵌官方网页（H5），完美校园没有可嵌的官方网页/SDK。**

| 想做的事 | 现实约束 |
|---|---|
| 在我们 App 的页面里显示/运行完美校园 App | 系统沙箱隔离：没有通用 API 可以把别的 App 的 Activity/界面嵌进自己的布局。`ActivityView` 一类跨 App 嵌入是系统/多窗口受限能力（普通应用不可用，且 minSdk 26 覆盖不到）；WebView 只能渲染网页、不能渲染 APK；`MediaProjection` 只能录屏/投屏（不可交互、需授权、不能后台）；分屏/画中画是系统级行为，不能在我们页面内嵌 |
| 通过官方 SDK 集成 | 完美校园没有对第三方开放"嵌入 App/SDK"；开放平台只是 HTTP API（且注册已停） |
| 深链直达"付款码/充值"页 | 即使有 scheme/App Links，也只是**跳转**到官方 App 的某个页面，用户仍在官方 App 内完成操作；完美校园未公开这类 scheme，需真机用 `adb shell am start` / manifest 确认 |
| 嵌微信/支付宝「完美校园」小程序 | 第三方 App 不能内嵌小程序页面，只能跳转（且需目标小程序 link/白名单） |
| 把官方 App 的登录/接口复刻进来 | 那是"复刻协议"，不是"集成官方 App"：需要逆 RSA/DES3/签名/device_id（单设备校验），违反平台协议风险高；校园码/充值属支付，绝不能做 |

**HFUT-Schedule 其实也没"集成"官方 App**：它对今日校园/完美校园只是 `Intent` 拉起官方 App（`com.wisedu.cpdaily`）；对慧新易校是 **WebView 打开官方 H5**（网页可嵌），不是嵌 App。这就是边界：**网页能嵌（WebView），App 只能跳转。**

**可做的最接近体验**：
1. 一键拉起完美校园 App（包名 `com.newcapec.mobile.ncp`，`getLaunchIntentForPackage`；未安装引导应用商店/官网）；
2. 真机确认有无 deep link/scheme → 有就直达付款码/充值页（仍是跳转）；
3. 若未来完美校园上线网页版卡页面（官方 2017 页面称"网页版正在研发"），才能用 WebView 内嵌。
