## 0. 结论摘要（先看这一页）

### 0.1 一句话结论

**「今日校园」的数据不要接进班级工具站；只做官方入口/外链（A 档）+ 公开信息（校历）自建（E 档）。** HFUT-Schedule 证明的是一条「CAS SSO → 学工系统 H5（`xsfw/sys/...`）→ WebView 注 cookie」的**技术路线**，不是一套可复用的「今日校园 API」；对 FJTCM 而言，这条路线在技术上可以照做、在合规上被本校校规与统一认证账号条款直接否定、在产品上收益≈0。（置信度：**高**）

### 0.2 判定总表

| 维度 | 判定 | 一句话理由 | 置信度 |
|---|---|---|---|
| **接口/技术可行性** | **中**（模式可行，FJTCM 侧未验证） | HFUT-Schedule 的「今日校园」= 学工系统 H5 容器 + CAS 票据 + `_WEU` cookie + WebView；金智 `xsfw/sys/<app>/*default/index.do` 是同族通用规律，但 FJTCM 的部署域名/是否信任本校 CAS 均属【需确认】 | 中 |
| **工程可行性** | **中**（A 档容易；数据接入是持续工程） | 站内已有 5 组成熟接入范式可复用：PGP 队列 + 本机 agent（课表 SSO）、`site_assets` 快照、ECS 微服务、定时采集、三端加工具；A 档 3–4 人日，C1 实时代理 10–15.5 人日 + 逆向 PoC 3–5 人日 | 高 |
| **合规/授权可行性** | **低 / 基本不可行** | 本校《信息系统用户管理规定》第十六条「不允许共享账号」；第二十六/二十七条第三方访问须合同 + 保密协议 + 部门许可 + 工具安全检查；统一认证账号仅限本人使用；2026 年多校公开把「诱导提供账密 + 自动化抓取」定性为违规 | 高 |
| **产品价值** | **低** | 今日校园是学校官方移动门户，学生端 9/10 项需求已覆盖且是**强制场景**（报修/审批/出入证/奖助/一卡通都在里面）；学生不可能因为班级站不装它；本站真正被需要的是官方没有的班级协作功能 | 高 |
| **综合结论** | **不推荐接入今日校园数据（NO-GO）**；推荐 **A（官方入口外链）+ E（不接，复用既有课表/电费数据）**；长期唯一正路 **D/F：学校授权后把班级 H5 上架进今日校园/办事大厅**（方向反过来） | — | 高 |

### 0.3 如果只记 5 件事

1. **三个系统别混**：HFUT-Schedule（合肥工大 FOSS 安卓客户端）≠ FJTCM 今日校园（金智教育 SaaS 官方门户）≠ 班级工具站。仓库里的「今日校园」代码，只是「用 CAS 票据登录学校学工系统、拉应用目录、塞进 WebView」。（事实）
2. **仓库没给出「今日校园 API」**：代码里定义了 **3 个学工系统接口**（实际只调用 1 个登录校验）；应用目录来自**内置快照 `assets/stu.json`（11 类 50 条应用 / 47 个唯一 appCode）+ 智慧社区 `listApplication` 动态补充**；页面本质是 **WebView 壳 + cookie 注入**。**不含成绩/课表**（这两项走教务）。仓库 `docs/HfutApi.md` 自己也写「学工系统登录参数比较多，估计要 JS 逆向」——**项目作者也没有把今日校园云 API 完整接出来**。（事实，详见 01 §3.3/§4）
3. **FJTCM 的今日校园是官方强制门户**：成绩/课表/奖助/报修/失物/水电余额/一卡通/邮箱/公告/校历，学生本来就必须装；把它的数据搬进班级站，边际收益 ≈「少点一次图标」。（事实，校方 2024-07 指南）
4. **合规是硬闸**：本校校规明文「不允许共享账号」，第三方访问信息系统还须合同/保密协议/许可/工具安全检查；代登录 = 把同学的统一认证账号交给第三方系统，校规层面即可被否定，不必等到 PIPL。（事实 + 推断）
5. **真正值得做的替代**：站内「官方入口」导航（今日校园 / 办事大厅 / 完美校园 / 教务）、校历/教学周自建（公开信息）、以及**用户自己粘贴/导入本人数据**的成绩分析——全部零接口、零凭据、零风险。长期若学校愿意，把班级 H5 **上架进**今日校园门户（D/F），才是既合规又有体验收益的方向。（推断，置信度中高）

## 1. 研究问题与结论边界

### 1.1 用户问题的三个层次

「把今日校园功能融入班级工具站」可以拆成三个完全不同的问题，混在一起谈会得出错误结论：

| 层次 | 问题 | 本报告结论 |
|---|---|---|
| **A. 接口层** | HFUT-Schedule 里的「今日校园」接口长什么样？能不能在 FJTCM 复刻？ | 能说清楚；**不能直接复刻**（见 §2）——仓库给的是「CAS + 学工 H5 + WebView」模式，不是通用 API；FJTCM 的部署细节未知 |
| **B. 工程层** | 班级工具站有没有能力接？接在哪？要多少人日？ | 有能力；A 档 3–4 人日、B 档 6–9 人日、C1 档 10–15.5 人日（+逆向 3–5）。（见 §4） |
| **C. 合规/产品层** | 该不该做？值不值得做？ | **不该**：校规禁止 + 无学校授权 + 官方已覆盖 + 维护永续（见 §5/§6） |

### 1.2 本报告明确回答 / 不回答

**回答**：仓库中与「今日校园」有关的全部接口与认证链路；这些接口的可迁移性；班级工具站现有接入面与三档改动量；技术/工程/合规/价值四维判定；推荐路线与前置条件。

**不回答 / 不能回答**：FJTCM 今日校园的真实部署域名、App 端 token 协议、签到/请假接口签名、学校是否已开「能力开放平台」、今日校园 SaaS 云 API（`*.campusphere.net`）的内部接口——这些**没有公开资料、也没有学校授权，本轮不做任何探测**，全部列入 §7 开放问题。

## 2. 接口分析：HFUT-Schedule 的「今日校园」到底做了什么

### 2.1 仓库定位与模块地图

- **项目**：`Chiu-xaH/HFUT-Schedule`（聚在工大），合肥工业大学本科生校园服务聚合 **Android 客户端**，Kotlin + Compose，Apache-2.0，默认分支 **`dev`**（[仓库](https://github.com/Chiu-xaH/HFUT-Schedule)）。README 自述覆盖教学/生活/校内服务 **40+ 场景**，2026-11 仍在活跃更新。
- **模块**：`app`（UI/业务/登录）、`network-api`（Retrofit 接口与数据模型）、`network-core`（OkHttp 封装）、`common-logic`/`common-ui`、`consumption-forecast`、`tools`（爬虫/验证码 OCR/WebVPN 等脚本）、`docs`（含一份 **`HfutApi.md` 校内 API 文档**，2024-11 完成）。
- **与「今日校园」相关的代码集中在 4 处**：

| 位置 | 文件 | 职责 |
|---|---|---|
| 接口定义 | `network-api/src/main/java/com/hfut/schedule/network/api/inf/StuService.kt` | 学工系统（今日校园）3 个接口 |
| 数据模型 | `network-api/.../model/response/json/stu/TodayCampusAppResponse.kt` | 应用目录 JSON（`datas[].categoryName`、`apps[].name/iconUrl/openUrl`） |
| 登录/认证 | `app/.../logic/network/inf/LoginService.kt`、`CasLoginRepository.kt`、`CasLoginType.kt`、`impl/LoginServiceCreator.kt`、`interceptor/AesKeyInterceptor.kt`、`interceptor/RedirectTicketInterceptor.kt` | CAS 统一认证 → 学工系统票据/cookie |
| 界面承载 | `app/.../ui/screen/home/search/function/school/student/TodayCampus.kt`、`ui/nav/destination/StuTodayCampusDestination.kt`、`logic/util/sys/Starter.kt`、`ui/component/webview/WebViewForNavigation.kt`、`ui/activity/util/WebViewActivity.kt`、`ui/util/WebViewFactory.kt`、`assets/stu.json` | 应用目录列表 + WebView 打开 + 离线兜底 + 一键拉起今日校园 App |

> **重要澄清（01 §3.3）**：3 个学工接口中**只有 `getConfigUserInfo.do` 存在实际调用**（登录态探测）；`jbxxapp/*default/index.do?ticket=` 与 `getFxYy.do` 在 899 个抓取文件中**只有定义、没有调用点**。也就是说：**今日校园页的应用目录主要靠内置快照 `stu.json` + 智慧社区动态目录**，不是每次登录都走 `getFxYy.do`。这进一步说明仓库做的是「入口壳」，不是「今日校园 API 客户端」。

> **注意不要被命名误导**：仓库里的 `UniAppService.kt` / `UniAppCampusHelper.kt` 是**合工大教务新微服务**（`jwglapp.hfut.edu.cn`，`eams-micro-server/api/v1/...`），不是今日校园；其登录需要微信 code，仓库作者注明「无法脱离微信使用」。今日校园相关的是 **`StuService` + `TodayCampus` + CAS 链**。

### 2.2 认证链路（CAS 统一认证，6 步）

HFUT 的 CAS 是**金智定制版**（`https://cas.hfut.edu.cn/`），与 Apereo CAS 的字段/加密不同，逐步如下（源码：`LoginService.kt`、`AesKeyInterceptor.kt`、`RedirectTicketInterceptor.kt`、`CasLoginRepository.kt`、`CasLoginType.kt`；文档：`docs/HfutApi.md` §「CAS统一认证」）：

| 步 | 请求 | 关键参数/响应 | 代码/文档证据 |
|---|---|---|---|
| 1 | `GET /cas/checkInitParams` | 响应头 `Set-Cookie` 中取 **`LOGIN_FLAVORING`**（同时作为后续密码 AES 加密的密钥）；JSON 返回是否需验证码（`vercode`） | `AesKeyInterceptor.kt`（提取 `LOGIN_FLAVORING` 存 SharedPrefs）；`CasFlavorSessionResponse.kt`（`vercode → needCaptcha`）；`docs/HfutApi.md` L26–31 |
| 2 | `GET /cas/login?service=<目标系统>` | 响应 HTML 中取 `input[name=execution]`（形如 `e1s1`）；`Set-Cookie` 取 `JESSIONID/SESSIONID` | `CasLoginRepository.kt::getCasCookie`（L61–79，Jsoup 解析 execution、取 Set-Cookie）；`docs/HfutApi.md` L8–19 |
| 3 | 若需验证码：`GET /cas/vercode` | 返回图片验证码；仓库另附 `tools/Captcha-Ocr`（Tesseract5 训练集）用于自动识别 | `docs/HfutApi.md` L21–24；`tools/Captcha-Ocr/README.md` |
| 4 | `POST /cas/login?service=<目标系统>`（表单） | `username`=学号；`password`=**AES(密码, LOGIN_FLAVORING)**；`execution`；`_eventId=submit`；`capcha`=验证码；**必须带 PC/手机 UA**，否则异常 | `LoginService.kt::loginCas`（L27–37）；`docs/HfutApi.md` L53–84；`CryptoUtil` 负责 AES |
| 5 | 成功 → `302 Location: ...?ticket=ST-...` | 拦截器判断 Location 命中目标系统域名后**手动再请求一次**（OkHttp 关闭自动跳转），从响应体/`Set-Cookie` 拿业务系统 cookie | `LoginServiceCreator.kt`（`allowAutoRedirect(false)` + `RedirectTicketInterceptor`）；`RedirectTicketInterceptor.kt` L17–37、L171–185 |
| 6 | 学工系统：`_WEU=<token>` | Location 命中 `stu.hfut.edu.cn` 时，重定向响应头 `Set-Cookie` 提取 **`_WEU`**，按 `prefix + value` 存入 `SharedPrefs("stu")`，Toast「学工系统登陆成功」 | `RedirectTicketInterceptor.kt::parseLoginStu`（L171–185） |

**CAS 目标系统注册表**（`CasLoginType.kt`）：教务 `JXGLSTU`、信息门户 `ONE`、**学工系统 `STU` = `https://stu.hfut.edu.cn/xsfw/sys/xgutilapp/userinfo/getConfigUserInfo.do`**、智慧社区、图书馆、智慧后勤、体测、指间工大、第二课堂。另有 OAuth2 变体 `GET /cas/oauth2.0/authorize?response_type=code&client_id=...&redirect_uri=...`（信息门户 `client_id=BsHfutEduPortal`），用于不支持 CAS service 参数的系统（`LoginService.kt` L47–54；`CasLoginRepository.kt` L46–59）。

### 2.3 今日校园（学工系统）接口清单

**基址**：`Constant.STU_URL = https://stu.hfut.edu.cn/`（`Constant.kt` L83；`StuServiceCreator.kt` 关闭自动跳转）。**认证方式**：第 6 步拿到的 `_WEU` cookie；部分接口另需 `ticket` 查询参数。

| # | 方法/路径 | 参数 | 返回/用途 | 失败语义 | 证据 |
|---|---|---|---|---|---|
| 1 | `GET /xsfw/sys/jbxxapp/*default/index.do` | `?ticket=ST-...` | 学工系统 H5 首页/会话建立（**定义但仓库内未见调用**；实际由拦截器手动 follow 完成换 cookie） | 无 ticket/过期 → 登录页 HTML | `StuService.kt` L14–17（01 §3.3） |
| 2 | `POST /xsfw/sys/xgutilapp/userinfo/getConfigUserInfo.do` | Header `Cookie: _WEU=...`；无 body（登录校验） | 返回含当前学生学号信息的 JSON；`OthersRepository.parseCheckStuLogin` 用「响应体包含学号」判定成功 | 不含学号 → 登录失败 | `StuService.kt` L17–18；`OthersRepository.kt` L161–172 |
| 3 | `POST /xsfw/sys/xggzptapp/modules/xszm/getFxYy.do` | Header `Cookie: _WEU=...`；表单 `data` = `{"FZDM":"SCYY","pageSize":"500","pageNum":1}` | 今日校园应用目录：`datas[]`（`categoryName` + `apps[]`，每个 app 有 `name/iconUrl/openUrl`） | 空/错误 JSON → 目录为空 | `StuService.kt` L19–27；**仓库内仅定义、未见调用**（01 §3.3） |
| 4 | `GET api//mobile/community/application/listApplication`（智慧社区） | Header `X-Access-Token`（智慧社区 token，由 `validateLogin?ticket=` 换得） | 动态应用目录：`{result:[{category, subList:[{name,logo,url}]}]}`；客户端只保留 `url` 以 `STU_URL` 开头的条目，归入「智慧社区」分组 | token 无效/空 → 不显示该分组 | `CommunityService.kt` L106–108；`CommunityRepository.kt` L342–357；`CommunityStuAppResponse.kt` |
| 5 | （应用内跳转）`openUrl` | WebView 注入 `Cookie: _WEU=...` 后加载 | 学工业务 H5 页面（50 个应用中 **31 个 `http://`、19 个 `https://`**，存在明文/混合内容风险） | 302/登录页 → 用户重新登录 | `TodayCampus.kt` L222/250/287/311；`Starter.kt` L217–253；`WebViewForNavigation.kt` L149–150；`stu.json` |

**应用目录模型**（`TodayCampusAppResponse.kt`）：

```json
{ "datas": [ { "categoryName": "学工服务",
               "apps": [ { "name": "学生请假",
                           "iconUrl": "https://.../xxx.png",
                           "openUrl": "http://stu.hfut.edu.cn/xsfw/sys/swmxsqjapp/*default/index.do" } ] } ] }
```

**内置离线目录**（`app/src/main/assets/stu.json`，45.4 KB）实际内容：**11 个分类、50 条应用（47 个唯一 appCode；3 对为本科生/研究生重复条目）**——学工服务 5、研工服务 9、迎新服务 1、队伍建设 2、就业工作 1、国防教育 3、健康管理 2、心理服务 11、学风建设 5、资助工作 7、日常管理 4。代表性应用：**学生请假、签到助手、节假日离校、健康信息收集、综合测评、奖学金/助学金/困难补助、心理普查/咨询、上课检查、晚自习检查、寝室文明、迎新、征兵咨询**。图标时间戳集中在 2021-01～2024-08，且目录**无自动更新机制**（只是内置快照）。

> 这张清单很关键：**今日校园（学工系统）承载的是「辅导员/学工流程类」应用**；成绩、课表、考试、空教室等教学数据在**教务系统**（HFUT 的 `jxglstu`/`eams`），不在这个目录里。因此「用今日校园接口做课表/成绩」这个设想，在仓库样本里**没有证据支持**。

### 2.4 界面承载方式（WebView + cookie 注入）

1. **列表页** `StuTodayCampusScreen`：**先展示内置快照 `assets/stu.json`**（`getTodayCampusApps`，`remember` 缓存）；`refreshNetwork` 用**智慧社区 token**（`prefs("TOKEN")`，不是学工 `_WEU`）拉动态目录补充，按 `openUrl` 相对路径去重后归入「智慧社区」分组；按 `categoryName` 分组渲染 2 列卡片，图标 `UrlImage`，点击卡片 `Starter.startWebUrlInner(context, openUrl, title=name, cookie=cookie)`（cookie = `prefs("stu")` 的 `_WEU`）。
2. **WebView**：`WebViewFactory.setInitial()` **先清空全部 Cookie**（`removeSessionCookies`/`removeAllCookies`），再 `CookieManager.setCookie(openUrl, "_WEU=...")`、flush 后才 `loadUrl`；请求级 `sharedInterceptRequest` 再补注。**注入的是学工 `_WEU`，不是 CAS TGC，也不把 ticket 放进 WebView URL**（ticket 只在 OkHttp 302 follow 中用一次）。
3. **离线/退路**：`StartAppIconButton` 直接**拉起官方今日校园 App**（`AppPackages.TODAY_CAMPUS("com.wisedu.cpdaily","今日校园")`，`Starter.kt` L43–64）；顶栏「学工系统」按钮用外部浏览器打开 `stu.hfut.edu.cn`（`TodayCampus.kt` L126–135）。
4. **扫码/其他登录**：`LoginService.kt` 还定义 `cas/app/qrCode`、`cas/app/query`、`cas/app/saveTGC` 等 App 扫码登录辅助接口（L57–75），用于 CAS 扫码登录场景。

### 2.5 实现要点与已知坑（01 §7 摘要）

| 坑 | 说明 | 对 FJTCM 移植的含义 |
|---|---|---|
| **验证码** | `cas/checkInitParams` 的 `vercode` 决定是否出图；仓库靠 Tesseract 自训 OCR（`tools/Captcha-Ocr`）或人工 | 自动化必须「过验证码」，等于规避学校安全控制；不做 OCR 就要人工，无法无人值守 |
| **AES key 依赖 Cookie** | 密码用 `LOGIN_FLAVORING` 的 Cookie 值做 AES-ECB 密钥；`AesKeyInterceptor` 未命中时会**把空串写回**（并发/首启失败 → 密码加密错误） | FJTCM 的 CAS 是 Apereo 形态（`pwdEncryptSalt` + AES-CBC，`jwxt.py` 已实现），**不能照搬 HFUT 的 LOGIN_FLAVORING 逻辑** |
| **ticket 一次性** | `ST-` ticket 用一次即废，每次刷新平台都要重新 `cas/login?service=` | 每次取数都要重新登录（或缓存 TGC/`_WEU`） |
| **Cookie 生命周期未知** | TGC/`_WEU` 有效期无解析；学工只能靠「响应含学号」探测失效，无 refresh token | 失效靠轮询自愈，体验/维护成本高 |
| **UA/风控** | CAS 必须 PC UA；文档提到教务会封 IP/拒绝响应；高频多平台登录易触发风控 | 70 人集中从 1 台服务器登录 = 典型批量行为，最容易被识别 |
| **HTTP 明文** | 50 个应用中 31 个是 `http://`，`_WEU` 会注入明文 URL；App 全局允许明文 | WebView 有混合内容/中间人风险；浏览器/HTTPS 站点更不能照搬 |
| **静默失败** | 学工登录失败只写日志、不提示用户 | 移植必须给明确失败态（否则用户以为已登录） |
| **凭据明文落盘** | 仓库把 CAS 账号密码明文存 SharedPreferences（`LoginUI.kt`/`SharedPrefs`） | **安全红线，绝不可复用**；任何实现都应「不落盘/DPAPI/PGP」 |
| **应用目录会过期** | `stu.json` 是内置快照、无自动更新 | 照搬会「目录越来越旧」；需动态拉取 + 兜底缓存 |
| **接口随时改版** | 仓库 `docs/HfutApi.md` 自述学工登录「需 JS 逆向」；无公开契约/SLA | 维护是永续对抗，不是一次性开发 |

### 2.6 可迁移性判定：哪些是金智通用规律，哪些是 HFUT 专属

| 层面 | 判定 | 依据 | 置信度 |
|---|---|---|---|
| 学工 H5 微服务路径规律 `xsfw/sys/<app>/*default/index.do` | **金智系通用规律**（同族学校可复用） | HFUT 50 个应用全部是此形态；第三方公开资料里其他金智学校 PC 端也是 `xsfw/sys/xggzptapp/*default/index.do`；金智部署文档出现 `/opt/wiseduAppGroups/xsfw`、`jbxxapp` 等目录 | 中高 |
| 应用目录 JSON（`datas[].apps[]`） | 同族通用（字段名基本一致） | 同族学工 App 的「应用中心」接口形态一致；HFUT 的 `getFxYy.do` 是金智标准模块路径 | 中 |
| CAS 登录细节（AES `LOGIN_FLAVORING`、`checkInitParams`、`execution e1s1`） | **HFUT 专属**（金智 CAS 定制版） | HFUT `cas.hfut.edu.cn`；FJTCM 是 `authserver.fjtcm.edu.cn`（Apereo CAS 形态，`jwxt.py` 用 `pwdEncryptSalt` + AES-CBC） | 高 |
| 今日校园 SaaS 云 API（App 内成绩/一卡通/水电等） | **仓库完全没有涉及** | `docs/HfutApi.md` L1720–1722 自述学工登录「参数比较多，估计要 JS 逆向」；仓库实现绕开学工 API，用 CAS 票据 + WebView | 高 |
| 今日校园 App 包名与「拉起官方 App」 | 可复用（`com.wisedu.cpdaily`） | `Starter.kt` L48；金智 `wisedu` 品牌 | 中高（包名需以 FJTCM 商店版本复核） |

**结论（技术层）**：这条路线对 FJTCM 的**可迁移部分**是「CAS 登录 + 学工 H5 应用目录 + WebView 注 cookie」，而**不可直接迁移**的是 HFUT 的 CAS 加密/参数；FJTCM 自己已有的 `jwxt/jwxt.py` 反而提供了 Apereo CAS 的现成实现（若真要做，认证层用它，而不是搬 HFUT 代码）。**但这一切的前提是**：FJTCM 的今日校园/学工 H5 确实走「本校 CAS 票据 + `xsfw`」——**本轮无法核实，属于最大未知数**（见 §7 Q1/Q3）。

> 对 FJTCM 的含义：`authserver.fjtcm.edu.cn` 属于 Apereo CAS 形态（IDS7 一类），今日校园很可能通过「IDS7/统一认证」或「代理层」接入；但**具体是哪种、是否允许第三方客户端用 CAS 票据进学工 H5、学工 H5 是否部署在公网**，均无公开资料。【需确认】

## 5. 可行性判定

### 5.1 判定口径

- **技术可行性**：不依赖学校授权、不代登录，是否能在班级内落地（「能靠逆向做到」不算可行）；
- **工程可行性**：站内是否有现成范式、改动面、人日、可回滚；
- **合规可行性**：校规/账号条款/PIPL/学校授权是否允许；
- **产品价值**：相对官方已提供同等能力的**边际价值**。

### 5.2 逐功能矩阵（精简）

| # | 今日校园能力 | 技术 | 合规/授权 | 账号风险 | 维护 | 班级价值 | 建议 |

### 5.3 接入形态对比（A–E，5 分制加权）

权重：合规 ×2、账号风险 ×2、技术 ×1、维护 ×1、价值 ×1.5（满分 7.5 归一为 5；账号风险为反向维度，5=风险最低）。

| 形态 | 技术 | 合规 | 账号风险 | 维护 | 价值 | 加权 | 判定 |
|---|---|---|---|---|---|---|---|
| **E 不接（复用既有）** | 5 | 5 | 5 | 5 | 3 | **4.60** | **主方案（GO）** |
| **D 官方授权/上架** | 4 | 5 | 5 | 4 | 4 | **4.53** | 唯一长期正路（前置拿不到，⏳） |
| **A 外链入口** | 5 | 5 | 5 | 5 | 2.5 | **4.50** | **立即做（GO）** |
| **B 安卓 WebView** | 3 | 2 | 3 | 3 | 3 | **2.73** | 不推荐（NO-GO） |
| **C 代登录（C1/C2）** | 3.5 | 1 | 1 | 2 | 4 | **2.07** | 不推荐（NO-GO，红线） |

**为什么 B 也不推荐**：它仍要求用户向第三方 App 提供统一认证账密（与校规/账号条款冲突，只是不落库降低了泄露面）；技术上 HFUT 是「原生 CAS 登录后把 cookie 注入 WebView」，若改成「用户在 WebView 里登录」，要处理验证码/扫码/多因子/UA 白名单/cookie 域/上传下载/支付拦截，工作量接近自研壳；金智 H5 还可能依赖容器桥（`bh-mobile-sdk` 的 `closeWebView` 等），裸 WebView 存在白屏/功能残缺风险；收益只是「少切一次 App」。

**为什么 C 不推荐**：一个 CAS 登录换来的数据面极宽（学工 token 可读成绩/考试/宿舍/图书馆等），**技术上无法「只要课表」**，违反最小必要；HFUT-Schedule 为维持登录专门训练了验证码 OCR 模型（`tools/Captcha-Ocr`），等于**以技术手段规避学校安全控制**；维护是永续对抗；失败代价由同学账号承担（封禁 7/30 天/永久）。

### 5.4 综合可行性判定

> **问：将今日校园功能融入班级工具站，可行吗？**
>
> **答：**
> 1. **接口/技术层：可分析、可复刻（中）。** HFUT-Schedule 的今日校园 = CAS SSO + 学工 H5 应用目录 + WebView 注 cookie；金智 `xsfw/sys/...` 模式可迁移，但 FJTCM 侧域名/协议/是否信任本校 CAS 全部未验证；且它**不提供**今日校园 App 的成绩/一卡通/水电等云 API。
> 2. **工程层：可落地（中高）。** 站内有 5 个现成零件，A 档 3–4 人日；C1 档 10–15.5 人日 + 逆向 3–5 人日；但 C 档把 70 人账号/数据集中到本机单点+单人维护，风险形态质变。
> 3. **合规层：不可行（高置信）。** 本校校规第十六条「不允许共享账号」+ 第二十六/二十七条第三方访问须合同/许可/工具检查；统一认证账号仅限本人；无学校书面授权 = 只能靠「学校不追究」的默许，而 2026 年治理风向正在关闭这个窗口。
> 4. **产品层：不值得（高置信）。** 今日校园是学校强制门户，学生端 9/10 需求已覆盖；班级站差异化功能一件都不依赖它；接入 = 用「永久维护 + 封号/约谈风险」换「少点一次图标」。
>
> **最终判定：按「合规、可持续地把今日校园功能搬进班级工具站」口径 —— 不可行 / 不推荐（NO-GO）。**
> **可行的替代（推荐）：A 档官方入口 + E 档不接 + 校历公开信息自建 + 个人数据自助导入。**
> **唯一长期正路：D/F——学校立项后，把班级工具做成 H5 上架进今日校园/办事大厅（「我们进官方」，而不是「官方数据进我们」）。**

## 6. 推荐路线与（若坚持要接的）最小路径

### 6.1 推荐的 A+E 路线（可在班级内立即做，零数据风险）

| 阶段 | 动作 | 人日 | 验收 |
|---|---|---|---|
| **S1（短期 0–1 周）** | 「官方入口」卡组：今日校园（安卓 intent 拉起官方 App / 网页给下载与官网链接）、网上办事大厅 `e.fjtcm.edu.cn`、完美校园、教务系统；文案明确「官方 App/官方门户，非本站功能」；小程序只做复制链接/引导 | 3–4（三端） | 三端可跳转；0 外部请求；无参数回传；手机比例 0 溢出 |
| **S2** | 校历/教学周自建：`tools/calendar.json`（开学日、周次、节假日、来源与更新日期）→ 作业 DDL、课表周次、大屏对齐 | 1–2 | 手工维护；来源标注；无外部请求 |
| **S3** | 把边界写进仓库：AGENTS.md §0 增「不代登录、不托管他人凭据、不采集今日校园/学工数据」（课表为存量例外、不扩展） | 0.5 | 红线可被后续会话检索 |
| **S4（中期）** | 个人数据自助导入：用户自己粘贴/上传本人成绩单/课表 → 前端解析 → 仅存本人、可删除（零接口、零凭据） | 1–3 | 只处理本人数据；删除入口可用 |
| **S5（可选）** | 校级公开信息转述：只抓「无需登录的公开页面」（公告/校历），标注来源与抓取时间；一旦需登录即停 | 1–2 | 页面可公开访问；来源/时间可见 |

### 6.2 如果一定要做 C1（仅作技术预案，不推荐）

**前置（缺一不可）**：① 学校书面授权（明确数据范围/只读/责任）；② 学校书面同意「允许代操作」——按 §3.3 判断现实中几乎不可能；③ 等保/安全评估；④ 凭据方案（用户明确授权 + PGP/DPAPI + 不落服务端明文 + 一键撤销 + 失败即停）；⑤ 字段白名单 + 仅本人可见 + 保留期 + 删除入口；⑥ 监控 + 改版告警 + **kill switch**；⑦ ≥2 人 + 老师 + 交接文档。

**技术骨架（复用 §4.2 零件 1/2）**：`tc_jobs`（sid/kind/params/pwd_pgp/status/过期，密码用后清空）→ 本机 `tc_agent.py` 认领（照 `diag_agent.process_login_jobs`）→ PGP 解密 → 用 **FJTCM 已有 `jwxt.py` 的 Apereo CAS 实现**（不要搬 HFUT 的 AES 版）→ 抓取/解析 → 写 `tc_cache`（仅本人可读）→ 前端 `rpc/tc_status`/`tc_get` 只读展示；`tc_enqueue` 做限流（每学号每小时 ≤3 次）+ agent 在线判定 + 幂等。**估计 10–15.5 人日 + 逆向 3–5 人日 + 合规/验收 1.5–2 人日。**

**为什么不建议**：以上 7 条前置里，第①/②条按本校校规和 2026 年治理风向基本拿不到；拿不到就只剩「灰产式代登录」，一旦学校加固（验证码/限校内网）或约谈，**功能全废 + 班级信任损失 + 可能追责**。

### 6.3 明确不建议做的（红线）

1. 在班级站（云端或本机）保存任何用户统一认证账号密码，或代任何人（含本人）登录学校系统；
2. 抓取今日校园/学工/教务数据用于班级站展示（课表存量链路保持「仅运营者本人、不扩展」）；
3. 用 iframe/反代把官方页面包装成站内功能，或在文案中暗示「本站可查成绩/课表/一卡通」；
4. 把含个人信息的今日校园数据落到香港 OSS 公共读（出境 + 公开）；
5. 由学院/辅导员/班委组织使用却未做教育 APP 备案使用者备案（若未来扩大到学院级）。
